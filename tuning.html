Конфигурация и тюнинг PostgreSQL

Главные параметры postgresql.conf: память, чекпоинты, autovacuum, подключения. Не «настройки на максимум», а понимание, что каждый параметр меняет, и как смотреть, помогло ли.

1. Память

shared_buffers

Размер буфер-пула Postgres — куда читаются страницы данных и индексов из диска.

-- Текущее значение:
SHOW shared_buffers;

-- Стартовая рекомендация: 25% оперативки сервера, но не больше 32 ГБ.
-- /etc/postgresql/16/main/postgresql.conf:
shared_buffers = 8GB

-- Применить:
-- shared_buffers требует рестарта (это область разделяемой памяти).
  • На больше 32 ГБ обычно не растёт эффект — дальше работает кеш ОС, который Postgres тоже использует.
  • Слишком маленький shared_buffers = много обращений в кеш ОС / диск. Слишком большой = двойное буферирование с кешем ОС.
  • Смотреть hit-ratio: pg_stat_database (blks_hit / (blks_hit + blks_read)) или расширение pg_buffercache.

work_mem

Сколько памяти разрешено каждой сортировке/хеш-операции, прежде чем уйти на диск.

-- На сессию:
SET work_mem = '64MB';

-- Глобально (postgresql.conf):
work_mem = 16MB

-- Подсмотреть, насколько хватает:
EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM orders ORDER BY total DESC LIMIT 100;
-- "Sort Method: external merge  Disk: 12345kB"  ← мало work_mem
-- "Sort Method: quicksort  Memory: 12345kB"     ← хватило
  • Опасно: work_mem — это лимит на каждую операцию. Один сложный запрос может породить 5 хеш-джойнов и 2 сортировки, потребив 7 × work_mem.
  • Реальный пик памяти ≈ max_connections × запросы × work_mem × число_операций.
  • Поднимай локально (SET LOCAL) для тяжёлых отчётов, а не глобально.
  • Связанный параметр: hash_mem_multiplier (PG 13+) — отдельный множитель для хеш-операций.

effective_cache_size

«Подсказка» планировщику, сколько данных, по его мнению, сейчас в кеше (Postgres + ОС).

-- Это не выделение памяти, а оценка для планировщика.
-- postgresql.conf:
effective_cache_size = 24GB

-- Стартовая рекомендация: 50–75% RAM сервера.

Чем больше значение, тем охотнее планировщик выбирает индексное чтение (Index Scan / Bitmap) вместо последовательного. Если значение слишком мало — планы получаются с лишними seq-scan-ами.

Параметр не резервирует память. Можно менять на лету (SIGHUP).

maintenance_work_mem

Память для VACUUM, CREATE INDEX, ALTER TABLE, REINDEX.

-- Поднимаем для разовых операций (миграции, ребилд индекса):
SET maintenance_work_mem = '1GB';
REINDEX INDEX CONCURRENTLY idx_orders_user_id;

-- Или глобально, но скромнее:
maintenance_work_mem = 256MB

Влияет на скорость восстановления из дампа, ребилда индексов и autovacuum. Autovacuum использует autovacuum_work_mem (по умолчанию = maintenance_work_mem).

2. WAL и чекпоинты

checkpoint_timeout, max_wal_size, checkpoint_completion_target

Чекпоинт — момент, когда «грязные» страницы пишутся на диск. Слишком частые — IO-всплеск; слишком редкие — долгий recovery.

-- postgresql.conf:
checkpoint_timeout = '15min'              -- максимум время между чекпоинтами
max_wal_size = '8GB'                      -- мягкий лимит размера WAL
min_wal_size = '1GB'                      -- держим минимум
checkpoint_completion_target = 0.9        -- размазываем запись на 90% интервала
wal_compression = on

-- Мониторинг:
SELECT * FROM pg_stat_bgwriter;
-- checkpoints_timed   — по таймауту (хорошо)
-- checkpoints_req     — по WAL-объёму (плохо, если много)
  • Если в pg_stat_bgwriter много checkpoints_req — max_wal_size мал, чекпоинты вынужденные. Поднимай.
  • checkpoint_completion_target = 0.9 размазывает запись по большей части интервала, снижая IO-пики.
  • На SSD/NVMe можно безопасно поднимать max_wal_size до десятков ГБ.
  • full_page_writes = on — обязательно на проде; защита от torn-page при сбое.

wal_level и архивирование

Сколько информации писать в WAL: минимум, репликация или логическая.

# postgresql.conf:
wal_level = replica          # минимум для физических реплик и PITR
# wal_level = logical        # для logical replication / CDC (Debezium)

archive_mode = on
archive_command = 'pgbackrest --stanza=main archive-push %p'

logical добавляет в WAL информацию для логической репликации; чуть-чуть больше объёма. Включай, только если реально используется (slot, publication, CDC).

3. Autovacuum

autovacuum_*: пороги срабатывания

Autovacuum нельзя выключать. Можно — настраивать частоту по конкретной таблице.

-- Глобальные пороги (postgresql.conf):
autovacuum = on
autovacuum_naptime = '1min'
autovacuum_vacuum_threshold = 50
autovacuum_vacuum_scale_factor = 0.2     -- VACUUM, если изменено 20% строк + 50
autovacuum_analyze_threshold = 50
autovacuum_analyze_scale_factor = 0.1    -- ANALYZE, если 10% строк + 50

-- Для горячих таблиц делаем агрессивнее:
ALTER TABLE orders SET (
  autovacuum_vacuum_scale_factor = 0.05,
  autovacuum_analyze_scale_factor = 0.02,
  autovacuum_vacuum_cost_delay = 2ms
);

-- Сколько dead-строк сейчас:
SELECT relname, n_live_tup, n_dead_tup,
       last_autovacuum, last_autoanalyze
FROM   pg_stat_user_tables
ORDER  BY n_dead_tup DESC
LIMIT  10;
  • scale_factor = 0.2 для огромной таблицы значит «трогать только когда обновлено 20% строк» — это редко. Снижай для горячих таблиц.
  • autovacuum_max_workers — сколько параллельных воркеров; обычно 3–5.
  • autovacuum_vacuum_cost_* — троттлинг IO. На проде иногда нужно понизить cost_delay, чтобы autovacuum успевал.
  • Никогда не выключай autovacuum. Альтернатива — перенастроить, не отключать.
  • Связано: Гайд: VACUUM.

4. Подключения и пулинг

max_connections vs PgBouncer

Каждое соединение — отдельный процесс, ~10 МБ памяти и слот в shared-памяти. Высокий max_connections — это всегда дорого.

-- postgresql.conf:
max_connections = 200             -- осторожно: каждое стоит RAM и shared mem
superuser_reserved_connections = 3

-- Текущая нагрузка:
SELECT state, count(*)
FROM   pg_stat_activity
GROUP  BY state;

-- Активные тяжёлые сессии:
SELECT pid, usename, application_name,
       now() - query_start AS dur, state, query
FROM   pg_stat_activity
WHERE  state <> 'idle'
ORDER  BY query_start
LIMIT  20;
  • Эмпирическая «верхняя граница без боли»: max_connections ≈ 4 × CPU cores. Дальше — пул.
  • Каждое соединение жрёт work_mem × кол-во операций при тяжёлом запросе. См. work_mem.
  • Сотни «idle» соединений — индикатор отсутствия пула на стороне приложения.

PgBouncer: режимы пулинга

Между приложением и Postgres ставится PgBouncer; тысячи клиентских коннектов превращаются в десятки серверных.

# pgbouncer.ini (минимум):
[databases]
app = host=db1 port=5432 dbname=app

[pgbouncer]
listen_addr = *
listen_port = 6432
auth_type = scram-sha-256
auth_file = /etc/pgbouncer/userlist.txt
pool_mode = transaction         # session | transaction | statement
default_pool_size = 25          # серверных соединений на одну (db, user)
max_client_conn = 2000          # клиентских — сколько хочешь
reserve_pool_size = 5
server_idle_timeout = 600

# Метрики:
psql -h 127.0.0.1 -p 6432 pgbouncer -U pgbouncer -c 'SHOW POOLS;'
  • session — серверный коннект держится, пока клиент не отпустит. Эквивалентно прямому подключению.
  • transaction — серверный коннект отдаётся обратно после COMMIT/ROLLBACK. Главный режим. Сессионные штуки (LISTEN, временные таблицы, SET вне транзакции, prepared statements клиента) ломаются.
  • statement — после каждого SQL. Совсем строгий, мультистейтмент-транзакции не работают.
  • Альтернативы: pgcat (Rust), встроенный пул в драйвере (HikariCP, asyncpg). Часто комбинируют: пул в драйвере + PgBouncer.

5. Планировщик и ввод-вывод

random_page_cost / seq_page_cost / effective_io_concurrency

Стоимости операций для планировщика и параллелизм случайного чтения.

-- На SSD/NVMe случайное чтение почти такое же быстрое, как последовательное:
SET random_page_cost = 1.1;        -- было 4.0
SET seq_page_cost    = 1.0;
SET effective_io_concurrency = 200; -- для bitmap heap scan

-- Глобально:
random_page_cost = 1.1
effective_io_concurrency = 200
  • Дефолтный random_page_cost = 4 рассчитан на HDD. На SSD/NVMe ставь 1.1–1.5 — иначе планировщик «боится» индексных чтений.
  • effective_io_concurrency — сколько параллельных чтений может выдержать диск. Для NVMe — 100–300.
  • jit = on ускоряет агрегации; на коротких OLTP-запросах может, наоборот, замедлять (компиляция дороже).
