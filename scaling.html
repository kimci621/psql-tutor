PostgreSQL · Масштабирование

Масштабирование, шардирование, CAP, PK и UUID

Как PostgreSQL «растягивается» вертикально и горизонтально, что такое шардирование и когда оно действительно нужно, теорема CAP и её практические следствия, выбор PK и работа с UUID.

1. Вертикальное и горизонтальное

Vertical vs Horizontal scaling

Сначала растягиваем одну машину, потом — несколько.

СтратегияЧто делаемКогда применять
Оптимизация запросовEXPLAIN, индексы, переписать SQLВсегда первым шагом
Vertical (scale up)больше CPU, RAM, NVMeПока хватает потолка одной машины
Read-replicasнесколько реплик на чтениеRead-heavy нагрузка
Партиционированиеодну большую таблицу режем на партицииСотни ГБ в одной таблице

Postgres сам по себе — single-master. «Горизонтально» в первую очередь означает реплики на чтение и продуманное партиционирование. Шардирование — ультима ратио.

2. Шардирование

Sharding — разбиение по ключу

Application-level или через расширения вроде Citus.

-- 1. Application-level: маршрутизирует приложение или прокси.
--    shard_id = user_id % N
--    запросы к шарду делаются по обычному соединению.

-- 2. Citus (расширение Postgres):
CREATE EXTENSION citus;

CREATE TABLE orders (
  id      bigint GENERATED ALWAYS AS IDENTITY,
  user_id bigint NOT NULL,
  total   numeric(12,2) NOT NULL,
  PRIMARY KEY (user_id, id)
);

SELECT create_distributed_table('orders', 'user_id');
-- теперь Citus сам распределяет данные между worker-нодами по user_id

Главное правило: проектируй ключ так, чтобы 95% запросов укладывались в один шард. Cross-shard JOIN-ы и транзакции — дорогая магия.

3. CAP / PACELC

Теорема CAP — и что из неё следует

При сетевом сбое распределённая система выбирает между Consistency и Availability.

CAP: при partition (P) системе остаётся выбор — отдать либо Consistency, либо Availability. Поэтому архитектуру характеризуют как CP или AP.

PACELC: расширение, говорящее, что выбор есть и в штатной работе — между Latency и Consistency. Postgres-кластер с синхронной репликацией — PC/EC; с асинхронной — PA/EL.

Важно: C из CAP — это linearizability, а C из ACID — выполнение ограничений БД. Не путай.

4. PRIMARY KEY и UUID

Что использовать в качестве PK

bigint identity (default), uuid v4, uuid v7/ULID, natural key.

-- Современный default — bigint identity, монотонно растущий:
id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY

-- UUID v4 (случайный) — легко генерить на клиенте:
id uuid PRIMARY KEY DEFAULT gen_random_uuid()

-- UUID v7 — упорядочен по времени (ULID),
-- сейчас обычно генерится приложением (драйвер/библиотека):
id uuid PRIMARY KEY  -- значение приходит извне
ТипРазмерЛокальность вставокКогда брать
bigint identity8 байтотличнаяВсе стандартные сценарии
uuid v416 байтплохаяРаспределённая генерация без координации
uuid v7 / ULID16 байтхорошаяТа же распределённая генерация, но уже без боли B-tree
natural key—зависитПочти никогда — нестабилен и неудобен для FK

UUID в PostgreSQL

Тип uuid и встроенный gen_random_uuid() с PG 13+.

SELECT gen_random_uuid();   -- встроено с PG 13

-- до PG 13 — через расширение:
CREATE EXTENSION IF NOT EXISTS pgcrypto;

CREATE TABLE events (
  id   uuid PRIMARY KEY DEFAULT gen_random_uuid(),
  ts   timestamptz NOT NULL DEFAULT now(),
  data jsonb
);

uuid хранится в 16 байтах (а не 36 символов канонического вида). Индексы по uuid в 1.5–2 раза больше, чем по bigint; UUID v4 ещё и плохо ложится в B-tree из-за случайности.

Сокращение UUID для UI/URL

22 символа base64url вместо 36 канонических.

-- 22 символа base64url (urlsafe), без padding:
SELECT replace(
         replace(
           rtrim(encode(uuid_send(gen_random_uuid()), 'base64'), '='),
         '+','-'),
       '/','_') AS short_id;

-- пример: cm5xR3a7T0WvO_aYpKJg5w

Base58 (без 0/O/I/l) тоже популярен: получится строка длиной 22 символа без визуально похожих знаков. Хранить в БД при этом продолжаешь обычный uuid — короткий вид нужен только для UI.

Часто на проде ставят реплику Postgres под аналитические запросы, чтобы не мешать «горячему» OLTP. Для time-series — TimescaleDB поверх Postgres.

6. Декларативное партиционирование

Когда таблица растёт до десятков и сотен миллионов строк, её разбивают на партиции по ключу — обычно по времени. Это ускоряет фильтры по диапазону и позволяет дропать старые данные одним DROP TABLE вместо VACUUM.

Декларативное партиционирование

Большие таблицы разбиваются на партиции по ключу.

CREATE TABLE events (
  id   bigint GENERATED ALWAYS AS IDENTITY,
  ts   timestamptz NOT NULL,
  data jsonb,
  PRIMARY KEY (id, ts)
) PARTITION BY RANGE (ts);

CREATE TABLE events_2026_05 PARTITION OF events
  FOR VALUES FROM ('2026-05-01') TO ('2026-06-01');

CREATE TABLE events_2026_06 PARTITION OF events
  FOR VALUES FROM ('2026-06-01') TO ('2026-07-01');

Старые партиции удаляются мгновенно (DROP TABLE), без VACUUM. Это часто и есть главный мотив секционирования.

7. Пулинг соединений

Postgres плохо переносит тысячи активных соединений — у каждого свой процесс. Решение — внешний пул, который мультиплексирует множество клиентских коннектов через небольшой пул серверных.

PgBouncer и пулы соединений

Pool modes: session / transaction / statement.

; pgbouncer.ini
[databases]
app = host=127.0.0.1 dbname=app

[pgbouncer]
pool_mode          = transaction
max_client_conn    = 5000
default_pool_size  = 20
server_reset_query = DISCARD ALL

В transaction-режиме одно серверное соединение делится между клиентами по транзакциям. Сессионные штуки (LISTEN, временные таблицы, prepared statements) при этом ломаются — учитывай в драйвере.
