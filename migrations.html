Миграции без даунтайма

В проде нельзя просто «дать ALTER TABLE и пойти спать». Любая блокировка таблицы под нагрузкой выстраивает за собой очередь транзакций и кладёт сервис. Эта страница — про дисциплинированный паттерн миграций, при котором схема и код движутся шаг за шагом, без окон обслуживания.

Паттерн expand → backfill → contract

Любое сложное изменение разбивается на три фазы. Сначала добавляем новое рядом со старым, потом плавно переносим данные, потом убираем старое. На каждой фазе сервис продолжает работать.

Безопасные миграции без даунтайма

Паттерн expand → backfill → contract.

-- 1. expand: добавляем новый столбец, код пишет в оба
ALTER TABLE users ADD COLUMN email_norm text;

-- 2. backfill маленькими батчами
UPDATE users SET email_norm = lower(email)
WHERE  id BETWEEN $1 AND $2 AND email_norm IS NULL;

-- 3. ограничения через NOT VALID, потом VALIDATE (без долгой блокировки)
ALTER TABLE users
  ADD CONSTRAINT users_email_norm_nn CHECK (email_norm IS NOT NULL) NOT VALID;
ALTER TABLE users VALIDATE CONSTRAINT users_email_norm_nn;

-- 4. contract: код переходит на email_norm, старый столбец дропается

Любой ALTER TABLE с ACCESS EXCLUSIVE выстраивает за собой очередь. Совмести с SET lock_timeout = '2s'; — лучше упасть и повторить, чем заморозить прод.

Идемпотентность операций

Любая надёжная распределённая система рано или поздно делает один и тот же запрос дважды. Идемпотентность — это когда второй раз ничего не происходит. Тот же принцип спасает миграции, повторённые после провала.

UNIQUE + ON CONFLICT и idempotency-ключ

Основной инструмент Postgres для идемпотентных вставок. И — антипаттерн, которого надо избегать.

-- идемпотентный INSERT через ON CONFLICT DO NOTHING:
INSERT INTO orders (id, user_id, total, idempotency_key)
VALUES ($1, $2, $3, $4)
ON CONFLICT (idempotency_key) DO NOTHING
RETURNING id;
-- если ничего не вернулось — запись уже была.

-- идемпотентный UPSERT — НЕ через сложение:
INSERT INTO inventory (sku, in_stock) VALUES ($1, $2)
ON CONFLICT (sku) DO UPDATE SET in_stock = EXCLUDED.in_stock;
-- (DO UPDATE SET in_stock = inventory.in_stock + EXCLUDED.in_stock — НЕ идемпотентно)

-- идемпотентные миграции через таблицу-журнал:
CREATE TABLE schema_migrations (
  version    text PRIMARY KEY,
  applied_at timestamptz NOT NULL DEFAULT now()
);

DO $$
BEGIN
  IF NOT EXISTS (SELECT 1 FROM schema_migrations
                 WHERE version = '2026_05_13_add_email_norm') THEN
    ALTER TABLE users ADD COLUMN email_norm text;
    INSERT INTO schema_migrations (version)
    VALUES ('2026_05_13_add_email_norm');
  END IF;
END$$;
  • Самый частый антипаттерн: in_stock + EXCLUDED.in_stock — выглядит как UPSERT, но повтор удваивает значение.
  • ON CONFLICT (col) требует UNIQUE-индекс на col. Без него — синтаксическая ошибка.
  • Идемпотентность по бизнес-ключу важнее, чем по PK: PK генерится автоматически и не совпадает между повторами.
  • Без RETURNING невозможно отличить «вставили» от «уже было» — для логов и аналитики критично.
