Безопасность PostgreSQL

Кто имеет право подключаться к серверу, по какому каналу, под какой ролью и с какими правами на объекты. Тема большая — здесь собраны главные кирпичи: pg_hba.conf, TLS, аутентификация, иерархия ролей, права на объекты и базовый аудит.

1. pg_hba.conf — кто может подключаться

Файл pg_hba.conf и порядок правил

Постгрес читает строки сверху вниз и применяет первую подходящую. Если ни одна не подошла — доступ запрещён.

# TYPE  DATABASE  USER          ADDRESS         METHOD
local   all       postgres                      peer
local   all       all                           scram-sha-256
host    all       app           10.0.0.0/8      scram-sha-256
hostssl all       reporter      0.0.0.0/0       scram-sha-256
hostnossl all     all           0.0.0.0/0       reject
host    replication repl_user   10.0.0.0/8      scram-sha-256
  • local — UNIX-сокет; host — TCP; hostssl / hostnossl — только зашифрованные / только незашифрованные.
  • peer сравнивает имя ОС-пользователя с именем роли (только для local) — удобно для локальной разработки и автоматики.
  • trust — без пароля. На проде запрещено всегда. На dev — только если знаешь, зачем.
  • После правки — SELECT pg_reload_conf(); или SIGHUP. Перезапуск сервера для этого не нужен.
  • Проверить, какая строка примерилась: SELECT * FROM pg_hba_file_rules;.

Методы аутентификации

Что именно проверяется и как: пароль, сертификат, GSSAPI/Kerberos, peer.

-- Включаем хеширование scram-sha-256 для всех новых паролей:
ALTER SYSTEM SET password_encryption = 'scram-sha-256';
SELECT pg_reload_conf();

-- Перевыпустить пароль роли в новом формате:
ALTER ROLE app WITH PASSWORD 'newpass';

-- Посмотреть, как роль хранится:
SELECT rolname, rolpassword IS NOT NULL AS has_password
FROM   pg_authid WHERE rolname = 'app';
  • scram-sha-256 — современный дефолт. Не передаёт пароль и хеш в открытом виде, защищён от replay-атак.
  • md5 — устаревший, оставлен для совместимости. Меняй на scram при первой возможности.
  • cert — клиентский сертификат TLS вместо пароля. Поле CN сравнивается с именем роли (или мапится через pg_ident.conf).
  • peer — только для local: имя ОС-пользователя ↔ имя роли.
  • gss / sspi — Kerberos / Windows домен. Нужно только в корпоративной инфраструктуре.

2. TLS / SSL

Включение TLS на сервере

Шифрует канал между клиентом и сервером; опционально проверяет сертификат клиента.

# postgresql.conf
ssl = on
ssl_cert_file = '/etc/postgresql/server.crt'
ssl_key_file  = '/etc/postgresql/server.key'
ssl_ca_file   = '/etc/postgresql/root.crt'   -- если проверяем клиентов

# pg_hba.conf — требовать SSL для удалённых:
hostssl   all   all   0.0.0.0/0   scram-sha-256
hostnossl all   all   0.0.0.0/0   reject
  • На стороне клиента — sslmode=verify-full. Это проверяет и шифр, и подпись CA, и совпадение hostname с CN сертификата.
  • sslmode=require — только шифр, без проверки подлинности (MITM возможен).
  • Проверить активную сессию: SELECT ssl, version, cipher FROM pg_stat_ssl WHERE pid = pg_backend_pid();.
  • На проде используй валидный сертификат от CA (Let's Encrypt / внутренний CA), не self-signed без проверки.

3. Роли и иерархия

Роли, группы и SET ROLE

В Postgres нет отдельных «пользователей» и «групп» — только роли. Право входа — атрибут LOGIN; группы — это роли без LOGIN, в которые включены другие роли.

-- Группа (без LOGIN):
CREATE ROLE app_readonly NOLOGIN;
CREATE ROLE app_writer   NOLOGIN;

-- Конкретные пользователи:
CREATE ROLE alice    LOGIN PASSWORD '...';
CREATE ROLE alice_ci LOGIN PASSWORD '...';

-- Включить пользователя в группы:
GRANT app_readonly TO alice;
GRANT app_writer   TO alice;

-- В сессии переключиться на роль группы (для проверки прав):
SET ROLE app_readonly;
SELECT current_user, session_user;   -- current=app_readonly, session=alice
RESET ROLE;
  • session_user — кто реально вошёл; current_user — чьи права действуют сейчас (после SET ROLE).
  • Атрибут INHERIT (по умолчанию) — права групп активируются автоматически. Без INHERIT их надо явно «надевать» через SET ROLE.
  • SUPERUSER обходит все проверки прав и RLS — выдавай только для admin-задач.
  • Для приложений правило: один пользователь БД на сервис, минимум прав, никаких SUPERUSER.

GRANT / REVOKE: что разрешать

Права действуют на уровне БД, схемы, объекта и колонки. Public-роль — особый «все остальные».

-- Жёсткий старт: убираем дефолтные права у PUBLIC.
REVOKE ALL ON SCHEMA public FROM PUBLIC;

-- Раздаём минимум:
GRANT USAGE ON SCHEMA public TO app_readonly, app_writer;

GRANT SELECT
  ON ALL TABLES IN SCHEMA public
  TO app_readonly;

GRANT INSERT, UPDATE, DELETE
  ON TABLE orders, order_items
  TO app_writer;

-- Чтобы права автоматически наследовались для новых таблиц:
ALTER DEFAULT PRIVILEGES IN SCHEMA public
  GRANT SELECT ON TABLES TO app_readonly;

-- Проверить эффективные права:
SELECT grantee, privilege_type
FROM   information_schema.table_privileges
WHERE  table_name = 'orders';
  • Без USAGE ON SCHEMA ни SELECT на таблицу не сработает — это частая ловушка.
  • ALTER DEFAULT PRIVILEGES назначает права на ещё не созданные объекты. Назначай от имени владельца таблиц.
  • GRANT … ON ALL TABLES IN SCHEMA — одноразовый снимок: новые таблицы прав не получат, для них нужен ALTER DEFAULT PRIVILEGES.
  • Для row-level granularity — Row-Level Security (см. RLS на senior-уровне).

Паттерн: read-only / writer / migrator

Готовая раскладка ролей, которую можно адаптировать под почти любой проект.

-- 1. Группы по ролям в системе:
CREATE ROLE app_readonly NOLOGIN;
CREATE ROLE app_writer   NOLOGIN;
CREATE ROLE app_migrator NOLOGIN;

-- 2. Права на схему/таблицы:
GRANT USAGE ON SCHEMA public TO app_readonly, app_writer, app_migrator;

GRANT SELECT          ON ALL TABLES IN SCHEMA public TO app_readonly;
GRANT INSERT, UPDATE, DELETE
                       ON ALL TABLES IN SCHEMA public TO app_writer;
GRANT ALL             ON SCHEMA public                TO app_migrator;
GRANT ALL             ON ALL TABLES IN SCHEMA public TO app_migrator;

-- Чтобы новые таблицы автоматически получали права:
ALTER DEFAULT PRIVILEGES IN SCHEMA public
  GRANT SELECT ON TABLES TO app_readonly;
ALTER DEFAULT PRIVILEGES IN SCHEMA public
  GRANT INSERT, UPDATE, DELETE ON TABLES TO app_writer;

-- 3. Логины приложения наследуют от групп:
CREATE ROLE svc_app   LOGIN PASSWORD '...' IN ROLE app_writer;
CREATE ROLE svc_bi    LOGIN PASSWORD '...' IN ROLE app_readonly;
CREATE ROLE svc_deploy LOGIN PASSWORD '...' IN ROLE app_migrator;

BI-сервис ходит под svc_bi и не может ничего испортить. Деплой/миграции — отдельный логин, чтобы можно было ротировать его пароль и не давать обычному приложению DDL-прав.

4. Аудит

Логирование и базовый аудит

Что ловить и где смотреть: log_connections, log_statement, расширение pgaudit.

# postgresql.conf
log_connections = on
log_disconnections = on
log_hostname = on
log_statement = 'ddl'           # 'all' тяжело и шумно
log_min_duration_statement = 200ms
log_line_prefix = '%t [%p] %u@%d app=%a '

-- pgaudit (расширение): тонкая настройка по классам и объектам.
CREATE EXTENSION IF NOT EXISTS pgaudit;
-- В postgresql.conf:
-- shared_preload_libraries = 'pgaudit'
-- pgaudit.log = 'ddl, role, write'

-- Кто что менял в правах — в журнале, плюс через pg_event_trigger:
SELECT * FROM pg_stat_activity WHERE state = 'active';
  • log_statement = 'all' на проде — это много гигабайт логов и потенциальная утечка PII; обычно ограничиваются 'ddl' + медленными запросами.
  • pgaudit даёт классы (READ, WRITE, FUNCTION, ROLE, DDL) и объектный аудит. Хорошо логируется в SIEM.
  • Для real-time реакции — EVENT TRIGGER (срабатывает на DDL).
  • Бэкапы и логи храни в другом доступе, чем сама БД, иначе компрометация одного снимает аудит.
