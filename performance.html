EXPLAIN и планировщик

Как Postgres решает, в каком порядке читать таблицы и какие индексы использовать, и как это всё прочитать самому. Это первая страница «эксплуатационного» трека: без чтения планов любые попытки тюнинга превращаются в гадание. Сюда же — поиск тяжёлых запросов через pg_stat_statements и настройки, которыми планировщик обычно гнут под железо.

Чтение плана запроса

EXPLAIN — это диалог с планировщиком. Сначала учимся читать его ответы.

Чтение EXPLAIN ANALYZE

Узлы плана: Seq Scan, Index Scan, Bitmap, Nested Loop / Hash / Merge Join.

EXPLAIN (ANALYZE, BUFFERS, VERBOSE)
SELECT u.email, count(o.id)
FROM   users u
LEFT JOIN orders o ON o.user_id = u.id
GROUP  BY u.email;

Сравнивай actual rows и rows estimated. Большая разница — устаревшая статистика или сложный предикат. BUFFERS покажет, сколько страниц прочитано из shared buffers и с диска.

Поиск тяжёлых запросов

EXPLAIN — точечный инструмент. Чтобы понять, какой запрос вообще оптимизировать, нужен агрегат по всему трафику.

pg_stat_statements — top тяжёлых запросов

Главный инструмент поиска того, что реально жрёт CPU и I/O.

CREATE EXTENSION IF NOT EXISTS pg_stat_statements;

SELECT round(total_exec_time::numeric, 1) AS total_ms,
       calls,
       round(mean_exec_time::numeric, 2)  AS mean_ms,
       round((100 * total_exec_time / sum(total_exec_time) OVER ())::numeric, 1) AS pct,
       query
FROM   pg_stat_statements
ORDER  BY total_exec_time DESC
LIMIT  20;

Ищи запросы по total_exec_time, а не по среднему: частый дешёвый запрос может быть дороже редкого тяжёлого.

Гнём планировщик

Когда план «не такой» — обычно дело не в багах планировщика, а в его представлении о железе и памяти.

WAL и контрольные точки

Каждое изменение сначала идёт в WAL (write-ahead log), и только потом разрешён COMMIT. Без этого нельзя ни тюнить запись, ни читать графики I/O.

SHOW wal_level;            -- minimal / replica / logical
SHOW checkpoint_timeout;   -- частота автоматических чекпойнтов
SHOW max_wal_size;         -- мягкий лимит, после которого чекпойнт срабатывает раньше

-- типовая настройка под write-нагрузку:
ALTER SYSTEM SET wal_compression = on;              -- +20–30% TPS на HDD
ALTER SYSTEM SET checkpoint_timeout = '15min';
ALTER SYSTEM SET max_wal_size = '8GB';
ALTER SYSTEM SET checkpoint_completion_target = 0.9;
SELECT pg_reload_conf();

-- сколько WAL накопилось и где мы сейчас по LSN:
SELECT pg_current_wal_lsn(),
       pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), '0/0')) AS wal_total;
  • Чекпойнт — момент, когда все «грязные» страницы сбрасываются на диск. Слишком частые — пик I/O в середине рабочего дня; слишком редкие — долгое recovery после сбоя.
  • Full-page writes: первое изменение страницы после чекпойнта попадает в WAL целиком. wal_compression = on сжимает эти страницы — почти бесплатный выигрыш.
  • archive_command должен быть надёжен: если он падает, Postgres копит WAL и в итоге останавливает запись. Простой rsync без --partial может оставить полуфайл — лучше pgBackRest или WAL-G.
  • На бэкапах и PITR WAL — основной материал; на репликации — поток между primary и репликой.

Параллельные планы

С PG 9.6 один запрос может использовать несколько CPU. Это бесплатно для аналитики, бесполезно для OLTP, иногда вредно при перегрузке.

SHOW max_parallel_workers;             -- бюджет на весь кластер
SHOW max_parallel_workers_per_gather;  -- максимум на один запрос
SHOW min_parallel_table_scan_size;     -- ниже этого порога — без параллелизма

-- посмотреть, что планировщик решил параллелить:
EXPLAIN (ANALYZE, VERBOSE)
SELECT user_id, sum(total)
FROM   orders
WHERE  created_at >= now() - interval '30 days'
GROUP  BY user_id;
-- ищи в плане: Gather, Parallel Seq Scan, Parallel Hash Join, Workers Launched

-- расширить под аналитический отчёт:
SET LOCAL max_parallel_workers_per_gather = 4;
SET LOCAL parallel_tuple_cost = 0.01;
SELECT ...;

-- выключить для конкретного запроса:
SET LOCAL max_parallel_workers_per_gather = 0;
  • OLTP-запросы (точечный SELECT по PK) параллелизм только замедляет — стоимость запуска воркеров больше выигрыша.
  • Parallel-aware узлы — не все. Триггеры, функции VOLATILE, CTE-MATERIALIZED, CURSOR — отрубают параллелизм для всего запроса.
  • Workers Launched: 0 — планировщик решил параллелить, но мест в общем бюджете не нашлось. Не путать с «не хотел».

Настройки планировщика

work_mem, effective_cache_size, random_page_cost.

SHOW work_mem;
SET LOCAL work_mem = '64MB';

-- На SSD имеет смысл понизить:
ALTER SYSTEM SET random_page_cost = 1.1;

-- Подсказать планировщику размер ОС-кеша:
ALTER SYSTEM SET effective_cache_size = '12GB';
SELECT pg_reload_conf();

work_mem применяется к каждому узлу-сортировке/хэшу в каждом подключении — не выкручивай глобально, поднимай локально для тяжёлых ETL.
