EXPLAIN и планировщик

Как Postgres решает, в каком порядке читать таблицы и какие индексы использовать, и как это всё прочитать самому. Это первая страница «эксплуатационного» трека: без чтения планов любые попытки тюнинга превращаются в гадание. Сюда же — поиск тяжёлых запросов через pg_stat_statements и настройки, которыми планировщик обычно гнут под железо.

Чтение плана запроса

EXPLAIN — это диалог с планировщиком. Сначала учимся читать его ответы.

Чтение EXPLAIN ANALYZE

Узлы плана: Seq Scan, Index Scan, Bitmap, Nested Loop / Hash / Merge Join.

EXPLAIN (ANALYZE, BUFFERS, VERBOSE)
SELECT u.email, count(o.id)
FROM   users u
LEFT JOIN orders o ON o.user_id = u.id
GROUP  BY u.email;

Сравнивай actual rows и rows estimated. Большая разница — устаревшая статистика или сложный предикат. BUFFERS покажет, сколько страниц прочитано из shared buffers и с диска.

Поиск тяжёлых запросов

EXPLAIN — точечный инструмент. Чтобы понять, какой запрос вообще оптимизировать, нужен агрегат по всему трафику.

pg_stat_statements — top тяжёлых запросов

Главный инструмент поиска того, что реально жрёт CPU и I/O.

CREATE EXTENSION IF NOT EXISTS pg_stat_statements;

SELECT round(total_exec_time::numeric, 1) AS total_ms,
       calls,
       round(mean_exec_time::numeric, 2)  AS mean_ms,
       round((100 * total_exec_time / sum(total_exec_time) OVER ())::numeric, 1) AS pct,
       query
FROM   pg_stat_statements
ORDER  BY total_exec_time DESC
LIMIT  20;

Ищи запросы по total_exec_time, а не по среднему: частый дешёвый запрос может быть дороже редкого тяжёлого.

Гнём планировщик

Когда план «не такой» — обычно дело не в багах планировщика, а в его представлении о железе и памяти.

Настройки планировщика

work_mem, effective_cache_size, random_page_cost.

SHOW work_mem;
SET LOCAL work_mem = '64MB';

-- На SSD имеет смысл понизить:
ALTER SYSTEM SET random_page_cost = 1.1;

-- Подсказать планировщику размер ОС-кеша:
ALTER SYSTEM SET effective_cache_size = '12GB';
SELECT pg_reload_conf();

work_mem применяется к каждому узлу-сортировке/хэшу в каждом подключении — не выкручивай глобально, поднимай локально для тяжёлых ETL.
