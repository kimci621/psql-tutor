PL/pgSQL, функции, процедуры и триггеры

Серверная логика на стороне Postgres: процедурный язык, отличие функций от процедур, триггеры. Главный совет — оставайся в чистом SQL, пока возможно; PL/pgSQL берут там, где без процедурного потока не обойтись.

1. PL/pgSQL

Основы PL/pgSQL

Переменные, IF/LOOP, исключения. Всё внутри блоков BEGIN…END.

CREATE OR REPLACE FUNCTION grant_bonus(uid bigint, amount numeric)
RETURNS numeric
LANGUAGE plpgsql AS $$
DECLARE
  new_balance numeric;
BEGIN
  UPDATE accounts
  SET    balance = balance + amount
  WHERE  user_id = uid
  RETURNING balance INTO new_balance;

  IF NOT FOUND THEN
    RAISE EXCEPTION 'нет аккаунта user_id=%', uid;
  END IF;

  RETURN new_balance;

EXCEPTION
  WHEN check_violation THEN
    RAISE NOTICE 'нарушено ограничение для user_id=%', uid;
    RETURN NULL;
END;
$$;

SELECT grant_bonus(42, 500);

Главное правило: где можно остаться в чистом SQL — оставайся. PL/pgSQL не оптимизируется так агрессивно, как обычный SQL, и сложнее в тестировании. BEGIN…END в PL/pgSQL — это блок кода, не транзакция; для управления транзакцией нужна процедура.

2. Функции и процедуры

FUNCTION vs PROCEDURE

Функция возвращает значение и работает в одной транзакции; процедура может управлять транзакцией.

-- Функция (LANGUAGE sql, простая):
CREATE OR REPLACE FUNCTION user_orders_count(uid bigint)
RETURNS bigint
LANGUAGE sql AS $$
  SELECT count(*) FROM orders WHERE user_id = uid;
$$;

SELECT user_orders_count(42);

-- Процедура (PG 11+, с COMMIT внутри):
CREATE OR REPLACE PROCEDURE archive_old_orders(days_old int)
LANGUAGE plpgsql AS $$
DECLARE
  rows_deleted int;
BEGIN
  LOOP
    DELETE FROM orders
    WHERE  ctid IN (
      SELECT ctid FROM orders
      WHERE  created_at < now() - (days_old || ' days')::interval
      LIMIT  1000
    );
    GET DIAGNOSTICS rows_deleted = ROW_COUNT;
    EXIT WHEN rows_deleted = 0;
    COMMIT;                       -- разрешено в PROCEDURE
  END LOOP;
END;
$$;

CALL archive_old_orders(365);

Функцию вызывают через SELECT, процедуру — через CALL. COMMIT/ROLLBACK внутри функции запрещены: функция всегда работает в рамках вызывающей транзакции. Процедура поэтому полезна для долгих фоновых задач (архивация, перенос), которые надо коммитить пачками.

3. Триггеры

Триггеры на BEFORE/AFTER INSERT/UPDATE/DELETE

Триггер вызывает функцию-триггер; функция возвращает запись (NEW) или NULL.

CREATE OR REPLACE FUNCTION set_updated_at()
RETURNS trigger
LANGUAGE plpgsql AS $$
BEGIN
  NEW.updated_at := now();
  RETURN NEW;
END;
$$;

CREATE TRIGGER trg_users_updated_at
BEFORE UPDATE ON users
FOR EACH ROW
WHEN (OLD.* IS DISTINCT FROM NEW.*)
EXECUTE FUNCTION set_updated_at();

-- STATEMENT-триггер для аудита:
CREATE OR REPLACE FUNCTION audit_orders_change()
RETURNS trigger LANGUAGE plpgsql AS $$
BEGIN
  INSERT INTO audit_log (table_name, op, who, ts)
  VALUES ('orders', TG_OP, current_user, now());
  RETURN NULL;     -- для AFTER STATEMENT можно NULL
END;
$$;

CREATE TRIGGER trg_orders_audit
AFTER INSERT OR UPDATE OR DELETE ON orders
FOR EACH STATEMENT
EXECUTE FUNCTION audit_orders_change();

BEFORE-триггер видит и может менять NEW; AFTER — выполняется уже после записи. FOR EACH ROW срабатывает на каждую строку, FOR EACH STATEMENT — раз на запрос.

Минусы: триггеры — невидимая магия. Через год коллега не поймёт, почему «само что-то меняется». Современные альтернативы — GENERATED ALWAYS AS … STORED-столбцы, явная логика в коде приложения, или RULE-системы для специфичных случаев.

4. Курсоры

Курсоры: проход по большому результату

Когда не нужно держать миллион строк в памяти сразу. DECLARE … FETCH … CLOSE.

-- Курсор внутри транзакции (psql):
BEGIN;

DECLARE c1 CURSOR FOR
  SELECT id, email
  FROM   users
  WHERE  is_active
  ORDER  BY id;

FETCH 5 FROM c1;        -- получить 5 строк
FETCH NEXT FROM c1;     -- ещё одну
MOVE FORWARD 100 IN c1; -- пропустить 100

CLOSE c1;
COMMIT;

-- В PL/pgSQL — синтаксический сахар FOR … IN:
CREATE OR REPLACE PROCEDURE recount_orders()
LANGUAGE plpgsql AS $$
DECLARE
  r record;
  total numeric;
BEGIN
  FOR r IN SELECT id FROM users WHERE is_active LOOP
    SELECT sum(o.total) INTO total
    FROM   orders o WHERE o.user_id = r.id;
    -- ... что-то делаем
  END LOOP;
END $$;

Серверный курсор живёт в рамках транзакции. Объявляй WITH HOLD, чтобы пережить COMMIT. Для большинства задач хватает обычного SELECT: драйверы и так читают результат лениво (libpq single-row mode, JDBC setFetchSize).

Курсор полезен, когда обработка строки запускает побочные действия (HTTP, запись в файл) и тянуть всё в память нельзя.

5. Динамический SQL: EXECUTE

EXECUTE и format()

Когда имя таблицы или столбца неизвестно заранее. Параметры — через USING, идентификаторы — через format(%I).

CREATE OR REPLACE FUNCTION row_count(tbl regclass)
RETURNS bigint
LANGUAGE plpgsql AS $$
DECLARE
  n bigint;
BEGIN
  -- Параметры подставляем безопасно через USING:
  EXECUTE format('SELECT count(*) FROM %s', tbl)
  INTO n;
  RETURN n;
END $$;

SELECT row_count('public.users');

-- Параметры значений идут через USING, не через format(%L)
-- (так EXECUTE их параметризует, как обычный prepared statement):
CREATE OR REPLACE FUNCTION find_by_email(addr text)
RETURNS users
LANGUAGE plpgsql AS $$
DECLARE
  u users;
BEGIN
  EXECUTE 'SELECT * FROM users WHERE lower(email) = lower($1)'
  INTO u
  USING addr;
  RETURN u;
END $$;

Идентификаторы (имена таблиц, столбцов) не параметризуются — для них используем format() с %I (квотирует, как идентификатор) или тип regclass, который сам валидирует имя.

Значения подставляй через USING — это безопасно (никаких SQL-injection) и кешируется планировщиком.

Не делай так: EXECUTE 'SELECT * FROM users WHERE email = ''' || addr || '''' — это инъекция.

6. Исключения и SQLSTATE

Классы ошибок (SQLSTATE) и условные обработчики

Каждая ошибка Postgres имеет 5-символьный код; в EXCEPTION WHEN можно ловить по имени класса.

-- Часто используемые имена условий (SQLSTATE → имя):
--   23505  unique_violation
--   23503  foreign_key_violation
--   23502  not_null_violation
--   23514  check_violation
--   22P02  invalid_text_representation
--   40001  serialization_failure
--   40P01  deadlock_detected
--   P0001  raise_exception (наш RAISE без указания SQLSTATE)

CREATE OR REPLACE FUNCTION safe_register(email_in text)
RETURNS bigint
LANGUAGE plpgsql AS $$
DECLARE
  uid bigint;
BEGIN
  INSERT INTO users(email)
  VALUES (lower(email_in))
  RETURNING id INTO uid;

  RETURN uid;

EXCEPTION
  WHEN unique_violation THEN
    SELECT id INTO uid FROM users WHERE email = lower(email_in);
    RETURN uid;
  WHEN check_violation THEN
    RAISE NOTICE 'check failed для %', email_in;
    RETURN NULL;
END $$;

-- Поймать любую ошибку (использовать редко — съедает диагностику):
EXCEPTION
  WHEN OTHERS THEN
    RAISE;       -- лучше пробросить дальше

Полный список — в документации, глава «PostgreSQL Error Codes». Класс — первые две цифры: 23 — нарушение целостности, 40 — сбой транзакции, 22 — ошибка данных, 42 — синтаксис/семантика.

Любой блок с EXCEPTION — это неявный SAVEPOINT: при ловле ошибки откатывается часть транзакции до начала блока. Поэтому ловить ошибки в горячем коде дорого.

Кастомные ошибки: RAISE … USING

Свои сообщения, свои SQLSTATE, и аккуратный диагностический трейс.

CREATE OR REPLACE FUNCTION transfer(from_id bigint, to_id bigint, amt numeric)
RETURNS void
LANGUAGE plpgsql AS $$
BEGIN
  IF amt <= 0 THEN
    RAISE EXCEPTION 'amount must be positive: %', amt
      USING ERRCODE   = 'invalid_parameter_value',  -- = '22023'
            HINT      = 'передавай число > 0',
            DETAIL    = format('from=%s to=%s amount=%s', from_id, to_id, amt),
            COLUMN    = 'amount',
            TABLE     = 'orders';
  END IF;

  -- ... перевод ...
END $$;

-- На стороне клиента (psql) увидишь:
--   ERROR:  amount must be positive: -10
--   DETAIL: from=1 to=2 amount=-10
--   HINT:   передавай число > 0
--   SQLSTATE: 22023

Хорошие правила: ERRCODE — выбирай существующий из стандарта или свой класс P0xxx. HINT — что делать, чтобы ошибка не повторилась. DETAIL — машиночитаемые подробности. Не суй секреты в текст ошибки — он может уехать в логи.

RAISE без аргументов внутри EXCEPTION просто перевыбрасывает текущую ошибку с её диагностикой.

7. RETURNS TABLE vs SETOF

RETURNS TABLE(...) vs RETURNS SETOF

Оба возвращают набор строк. Разница — в способе описания формы результата.

-- 1. RETURNS SETOF существующего типа (например, таблицы):
CREATE OR REPLACE FUNCTION active_users()
RETURNS SETOF users
LANGUAGE sql AS $$
  SELECT * FROM users WHERE is_active AND deleted_at IS NULL;
$$;

SELECT id, email FROM active_users();

-- 2. RETURNS TABLE(...) — анонимный тип, удобно для вычисляемых полей:
CREATE OR REPLACE FUNCTION user_summary()
RETURNS TABLE (id bigint, email text, orders_count bigint, spent numeric)
LANGUAGE sql AS $$
  SELECT u.id, u.email,
         count(o.id),
         coalesce(sum(o.total) FILTER (WHERE o.status = 'delivered'), 0)
  FROM   users u
  LEFT JOIN orders o ON o.user_id = u.id
  GROUP  BY u.id, u.email;
$$;

SELECT * FROM user_summary() WHERE spent > 1000;

-- 3. RETURNS SETOF record — без описания формы; нужно указывать его при вызове:
CREATE OR REPLACE FUNCTION pivot_raw()
RETURNS SETOF record
LANGUAGE sql AS $$
  SELECT category, count(*) FROM products GROUP BY 1;
$$;

SELECT * FROM pivot_raw() AS t(category text, n bigint);  -- иначе ошибка

RETURNS TABLE(...) — это синтаксический сахар над RETURNS SETOF record + OUT-параметры; форма результата известна, и вызов SELECT * FROM f() работает без расширения.

RETURNS SETOF <table> удобен, если функция отдаёт «обычные» строки таблицы — никакой переписи типа.

RETURNS SETOF record без описания — последнее средство: придётся указывать колонки в каждом вызове, и оптимизатор почти ничего не знает о результате.
