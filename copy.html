COPY и массовая загрузка

Загружать миллионы строк INSERT-ами — медленно. COPY — родной способ Postgres перекачивать данные пачкой; на нём же построены pg_dump и pg_restore.

1. Форматы COPY

Text, CSV, Binary

Три формата, разная скорость и компромиссы.

-- TEXT (по умолчанию): tab-separated, NULL = '\N'.
COPY users (id, email) TO '/tmp/users.tsv';
COPY users (id, email) FROM '/tmp/users.tsv';

-- CSV: с заголовками, кавычками, выбираемыми разделителями.
COPY users (id, email, full_name)
  TO '/tmp/users.csv'
  WITH (FORMAT csv, HEADER, DELIMITER ',', QUOTE '"', NULL '');

COPY users (id, email, full_name)
  FROM '/tmp/users.csv'
  WITH (FORMAT csv, HEADER);

-- BINARY: точный, типобезопасный, нечитаемый глазами.
COPY orders TO '/tmp/orders.bin' WITH (FORMAT binary);
COPY orders FROM '/tmp/orders.bin' WITH (FORMAT binary);
  • TEXT — компактнее CSV, но без HEADER и со специальными escape-ами (\t, \n, \\).
  • CSV — стандарт обмена с другими системами; чуть медленнее.
  • BINARY — самый быстрый и точный (типы сохраняются один-в-один), но привязан к версии Postgres и порядку байт. Между разными СУБД не переносится.

2. STDIN / STDOUT и клиентский COPY

\copy в psql и COPY ... FROM STDIN

Когда сервер не имеет доступа к файлам клиента.

# \copy в psql — выполняется на стороне клиента, файл читается локально.
psql -d app -c "\copy users FROM '/local/path/users.csv' WITH (FORMAT csv, HEADER)"

# Альтернатива: COPY ... FROM STDIN с пайпом:
cat users.csv | psql -d app -c "COPY users FROM STDIN WITH (FORMAT csv, HEADER)"

# Из приложения (драйвер):
# Python (psycopg):
#   with conn.cursor() as cur:
#       with open('users.csv', 'rb') as f:
#           cur.copy_expert("COPY users FROM STDIN WITH (FORMAT csv, HEADER)", f)
  • COPY 'path' читает файл на сервере — нужен доступ суперпользователя или роль pg_read_server_files.
  • \copy в psql — то же, но через STDIN. Файл доступен только клиенту, серверу никаких прав не нужно.
  • Драйверы (psycopg, pgx, JDBC) умеют COPY-протокол напрямую — стандартный способ загрузки из приложения.

3. Тюнинг массовой загрузки

Что выкрутить для разовой большой загрузки

Снимаем индексы и FK, поднимаем память, потом возвращаем.

-- 1. Готовим целевую таблицу (новый кластер или пустая):
ALTER TABLE big_table SET UNLOGGED;       -- если можно потерять при крэше
DROP INDEX IF EXISTS idx_big_*;

-- 2. На сессию:
SET maintenance_work_mem = '1GB';
SET synchronous_commit  = off;            -- риск потерять последнее на крэше
SET work_mem            = '128MB';

-- 3. Сама загрузка:
COPY big_table FROM '/data/big.csv' WITH (FORMAT csv, HEADER);

-- 4. Возвращаем:
ALTER TABLE big_table SET LOGGED;
CREATE INDEX idx_big_a ON big_table (a);
CREATE INDEX idx_big_b ON big_table (b);
ANALYZE big_table;
RESET synchronous_commit;
  • UNLOGGED-таблицы пишут только в heap, не в WAL — на порядок быстрее, но не реплицируются и теряются при крэше.
  • Создавать индексы после загрузки в разы быстрее, чем поддерживать их во время COPY.
  • Внешние ключи проверяются на каждой вставке — на массовой загрузке часто их временно отключают (ALTER TABLE ... DISABLE TRIGGER ALL), но это требует осторожности — нарушения уйдут незамеченными.
  • После загрузки — обязательно ANALYZE: иначе планировщик не знает статистику новых данных.

4. COPY ... FROM PROGRAM

Загрузка из конвейера

Запустить команду на сервере и принять её stdout как COPY-вход.

-- из gzip-файла на сервере:
COPY users FROM PROGRAM 'gunzip -c /data/users.csv.gz'
  WITH (FORMAT csv, HEADER);

-- из удалённой таблицы через postgres_fdw:
COPY local_users FROM PROGRAM 'psql -h remote -d app -c "\\copy users TO STDOUT WITH (FORMAT csv)"'
  WITH (FORMAT csv);

-- генерация на лету:
COPY ts FROM PROGRAM 'date -u +%FT%T'
  WITH (FORMAT csv);
  • Команда выполняется на сервере от имени роли postgres. Это серьёзная привилегия — по умолчанию доступно только суперпользователю.
  • С PG 11 есть роль pg_execute_server_program — можно делегировать без полного SUPERUSER.
  • Не трогай эту функцию, если не уверен в безопасности окружения.

5. COPY vs pg_dump

Когда что использовать

Оба используют COPY-протокол под капотом, но решают разные задачи.

ЗадачаИнструмент
Загрузить CSV из внешней системыCOPY ... FROM или \copy
Выгрузить таблицу как CSV для другой системыCOPY ... TO
Перенести БД целиком (структура + данные)pg_dump -Fc + pg_restore -j
Перенести только данные таблицы между Postgres-кластерамиCOPY TO STDOUT | COPY FROM STDIN
Логическая репликация / CDClogical replication, Debezium
Параллельный restore из дампаpg_restore -j N (см. backup → parallel restore)
