Частые ошибки PostgreSQL

Сборник сообщений, с которыми сталкиваешься чаще всего. Для каждой ошибки описана причина, пример воспроизведения и пути исправления. Кнопка «Поучиться с ИИ» открывает диалог: ментор сначала объяснит ошибку, затем поможет диагностировать её наводящими вопросами.

relation "X" does not exist

SQLSTATE 42P01

Сервер не нашёл таблицу с таким именем в текущем search_path.

Воспроизведение
SELECT * FROM Users;        -- если таблица называется "Users" с кавычками
SELECT * FROM other.users;  -- схема other отсутствует или нет прав
Причины
  • опечатка в имени таблицы или схемы;
  • таблица создавалась с двойными кавычками — теперь имя чувствительно к регистру;
  • нужная схема не входит в search_path;
  • у роли нет прав USAGE на схему — таблицу «не видно».
Как исправить
  1. Проверь SHOW search_path; и при необходимости расширь его.
  2. Используй полное имя schema.table.
  3. Найди реальное имя через \dt *.X в psql.

duplicate key value violates unique constraint "..."

SQLSTATE 23505

Нарушено уникальное ограничение (PRIMARY KEY или UNIQUE).

INSERT INTO users (email) VALUES ('a@example.com')
ON CONFLICT (email) DO NOTHING;
Что делать
  • посмотри, какой именно индекс упомянут в сообщении (имя в кавычках);
  • если это идемпотентная вставка — добавь ON CONFLICT;
  • если это гонка двух транзакций — нужна транзакция с SELECT … FOR UPDATE или повторная попытка.

null value in column "X" violates not-null constraint

SQLSTATE 23502

В обязательный столбец передан NULL — явно или потому что он отсутствует в INSERT.

ALTER TABLE users ALTER COLUMN email SET DEFAULT '';
-- или передать значение явно при INSERT

insert or update on table "..." violates foreign key constraint

SQLSTATE 23503

Запись ссылается на несуществующего родителя или родителя удаляют без CASCADE.

ALTER TABLE orders DROP CONSTRAINT orders_user_id_fkey,
  ADD CONSTRAINT orders_user_id_fkey
  FOREIGN KEY (user_id) REFERENCES users(id) ON DELETE CASCADE;
Что проверить
  • порядок вставок: сначала родитель, потом ребёнок;
  • правила ON DELETE и ON UPDATE;
  • вспомогательные индексы на FK-столбцах для производительности.

syntax error at or near "…"

SQLSTATE 42601

Ошибка синтаксиса. Сервер указывает позицию символа, на котором парсер «сорвался».

SELECT id, name FROM users WHERE id = 1;
Типичные причины
  • висящая запятая перед FROM;
  • зарезервированное слово в качестве имени без кавычек ("order");
  • незакрытая строка или кавычка;
  • точка с запятой внутри блока, где её быть не должно.

permission denied for table / relation / schema

SQLSTATE 42501

Ролью не выдан нужный набор прав. Часто помогает связка USAGE на схему + права на таблицы.

GRANT USAGE  ON SCHEMA public TO app_user;
GRANT SELECT, INSERT, UPDATE, DELETE
  ON ALL TABLES IN SCHEMA public TO app_user;

ALTER DEFAULT PRIVILEGES IN SCHEMA public
  GRANT SELECT, INSERT, UPDATE, DELETE ON TABLES TO app_user;

division by zero

SQLSTATE 22012

Попытка деления на ноль в выражении.

SELECT a / NULLIF(b, 0) FROM t;

NULLIF(b, 0) заменит ноль на NULL, и результат деления тоже станет NULL. Если нужно конкретное значение — оберни в COALESCE.

invalid input syntax for type …

SQLSTATE 22P02 / 22008

Строку не удалось привести к нужному типу: дате, числу, uuid и т. п.

-- Плохо: формат зависит от datestyle
SELECT '07.05.2026'::date;

-- Хорошо: явный формат
SELECT to_date('07.05.2026','DD.MM.YYYY');

deadlock detected

SQLSTATE 40P01

Две транзакции взаимно ждут блокировок друг друга. Postgres сам выбирает «жертву» и откатывает её.

-- Транзакция A: UPDATE accounts WHERE id = 1;
-- Транзакция B: UPDATE accounts WHERE id = 2;
-- Транзакция A: UPDATE accounts WHERE id = 2;  -- ждёт B
-- Транзакция B: UPDATE accounts WHERE id = 1;  -- → deadlock

Решение: упорядочивай захват блокировок (всегда по id ASC), уменьшай время удержания, добавляй retry.

could not serialize access due to concurrent update

SQLSTATE 40001

Сериализационный конфликт в REPEATABLE READ или SERIALIZABLE. Это не баг, а контракт уровня изоляции — нужен retry.

BEGIN ISOLATION LEVEL SERIALIZABLE;
-- ваши запросы
COMMIT;
-- при ошибке 40001 повторить транзакцию (с экспоненциальной задержкой)

too many connections / out of shared memory

SQLSTATE 53300 / 53200

Превышен лимит подключений или закончилась общая память.

SHOW max_connections;
SELECT count(*) FROM pg_stat_activity;
SELECT pid, state, query
FROM   pg_stat_activity
WHERE  state <> 'idle' AND backend_type = 'client backend'
ORDER  BY query_start;

Реальное решение — пуллер соединений (PgBouncer/PgPool) и закрытие idle-сессий.

canceling statement due to statement timeout

SQLSTATE 57014

Запрос превысил statement_timeout. Ставится в постгресе целенаправленно, чтобы запросы-«утечки» не висели.

-- На уровне сессии:
SET statement_timeout = '5s';

-- Постоянно для роли:
ALTER ROLE app_user SET statement_timeout = '5s';

database "X" is being accessed by other users

SQLSTATE 55006

К БД подключены клиенты, поэтому её нельзя удалить или переименовать.

SELECT pg_terminate_backend(pid)
FROM   pg_stat_activity
WHERE  datname = 'shop' AND pid <> pg_backend_pid();

DROP DATABASE shop WITH (FORCE);

role "X" already exists / does not exist

SQLSTATE 42710 / 42704

Перед удалением роли отзывай её права и переназначай владение объектами.

REASSIGN OWNED BY old_user TO new_user;
DROP OWNED BY old_user;
DROP ROLE IF EXISTS old_user;

Тексты сообщений ошибок воспроизведены так, как их выдаёт сервер PostgreSQL.
