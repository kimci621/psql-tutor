PostgreSQL · Репликация

Репликация PostgreSQL

Чтобы выдержать рост и пережить отказ одного сервера, нужна вторая копия данных, синхронизируемая в реальном времени. Эта страница — про два мира репликации Postgres (физический и логический), про то, как выбирать между sync и async, и про оркестрацию failover-а.

Что такое репликация в Postgres

Старт: какие виды бывают и как они выглядят на уровне команд. Подробности — в следующих секциях.

Репликация: streaming и logical (обзор)

Read-replica, failover, выборочная подписка.

-- логическая репликация:
CREATE PUBLICATION app_pub FOR TABLE orders, users;

CREATE SUBSCRIPTION app_sub
  CONNECTION 'host=primary dbname=app user=repl password=...'
  PUBLICATION app_pub;

-- лаг физической реплики:
SELECT now() - pg_last_xact_replay_timestamp() AS lag;

Два мира: физическая репликация WAL — копия кластера побайтно; логическая — поток изменений на уровне строк через decode WAL. Ниже разбираем по отдельности.

Гарантии доставки: sync vs async

Один из главных компромиссов в HA — как далеко может «убежать» primary относительно реплики, и кто за это платит латентностью.

Синхронная vs асинхронная

Стоит ли primary ждать подтверждения реплики на COMMIT.

-- postgresql.conf на primary:
synchronous_commit = on              -- (по умолчанию) ждать flush WAL локально
synchronous_standby_names = 'ANY 1 (replica1, replica2)'  -- + ждать любой 1 реплики

-- Уровни synchronous_commit:
--   off              — не ждать вообще (быстро, можно потерять последние транзакции при крэше)
--   local            — flush WAL локально
--   on (default)     — flush локально + если синхронная реплика, её LSN
--   remote_write     — реплика приняла, но ещё не записала на диск
--   remote_apply     — реплика применила и видит данные

-- На уровне сессии можно ослабить синхронный коммит для нечувствительных транзакций:
SET LOCAL synchronous_commit = local;
INSERT INTO audit_log (...) VALUES (...);  -- не критично для бизнеса
  • Async (по умолчанию) — primary не ждёт реплики. Быстрее, но при сбое возможна потеря последних транзакций.
  • Sync — нужно подтверждение от хотя бы одной реплики. Нулевая потеря, но повышенная latency и риск зависания при отказе всех синхронных реплик.
  • ANY 1 (...) — достаточно одной из перечисленных; FIRST 1 (...) — приоритет по порядку.
  • remote_apply — единственный уровень, где «прочитал на реплике сразу после COMMIT» работает гарантированно. Самый дорогой.

Replication slots

Слот — то, что гарантирует, что primary не выкинет WAL раньше, чем подписчик его прочитает. И то, что чаще всего «забивает диск» при инцидентах.

Replication slots и wal_keep_size

Слот гарантирует, что primary сохранит WAL, пока подписчик не догонит.

-- Создать физический слот (для streaming-реплики):
SELECT pg_create_physical_replication_slot('replica1');

-- Логический слот (для logical replication / CDC):
SELECT pg_create_logical_replication_slot('cdc_app', 'pgoutput');

-- Что в слотах сейчас:
SELECT slot_name, slot_type, active, restart_lsn,
       pg_size_pretty(pg_wal_lsn_diff(pg_current_wal_lsn(), restart_lsn)) AS retained_wal
FROM   pg_replication_slots;

-- Удалить заброшенный слот (он держит WAL и пухнет):
SELECT pg_drop_replication_slot('replica1');

-- Альтернатива слотам — вручную указанный объём WAL:
-- postgresql.conf:
wal_keep_size = '4GB'   -- оставлять 4 ГБ WAL независимо от слотов
max_slot_wal_keep_size = '8GB'  -- защита: слот не может удерживать больше
  • Без слота — реплика отстала, WAL ротировался, реплика навсегда сломалась. Приходится переинициализировать.
  • Со слотом — primary держит WAL, пока подписчик не подтвердит. Это безопасно, но заброшенный слот пухнет и может забить диск.
  • max_slot_wal_keep_size (PG 13+) ограничивает рост — лучше потерять одну реплику, чем primary.
  • wal_keep_size заменил старый wal_keep_segments с PG 13.

Failover и оркестрация

Когда primary падает, кто-то должен решить «теперь главный — реплика 2», переключить трафик и не привести к split-brain. Это работа оркестратора.

Failover и оркестрация: Patroni / pg_auto_failover / repmgr

Что делает «оркестратор» и зачем он нужен в проде.

# Patroni — самое распространённое решение.
# /etc/patroni/patroni.yml (упрощённо):
scope: pg-cluster
namespace: /pg/
name: node1

restapi:
  listen: 0.0.0.0:8008

etcd3:
  hosts: etcd1:2379,etcd2:2379,etcd3:2379

bootstrap:
  dcs:
    ttl: 30
    loop_wait: 10
    retry_timeout: 10
    maximum_lag_on_failover: 1048576
    postgresql:
      use_pg_rewind: true

postgresql:
  listen: 0.0.0.0:5432
  data_dir: /var/lib/postgresql/16/main
  authentication:
    replication: { username: replicator, password: ... }
    superuser:   { username: postgres,   password: ... }

# Команды:
patronictl -c patroni.yml list
patronictl -c patroni.yml switchover
patronictl -c patroni.yml failover
  • Patroni — Python, требует распределённое хранилище состояния (etcd / Consul / ZooKeeper). Самое богатое решение, индустриальный стандарт.
  • pg_auto_failover (CitusData) — без внешнего DCS; проще на старте, меньше возможностей.
  • repmgr — старая школа, без авто-failover-а; нужен внешний триггер.
  • Поверх любого из них — балансировщик / DNS / VIP, чтобы клиент знал, кто primary. Часто это HAProxy или PgBouncer + Patroni REST.
  • Switchover — управляемая смена ролей; failover — аварийная при недоступности primary.
  • pg_rewind возвращает старого primary в кластер быстрее, чем pg_basebackup.

Logical decoding и CDC

Logical decoding превращает WAL в поток событий «строка изменена». На этом строятся CDC-конвейеры (Debezium, wal2json) и кросс-версионная репликация. Без понимания replica identity и слотов это не запустить.

Logical decoding и Debezium

Замена событийной шине: каждый INSERT/UPDATE/DELETE превращается в событие, которое подписчик читает через replication-протокол.

-- 1. включаем logical-уровень WAL (требует restart):
ALTER SYSTEM SET wal_level = 'logical';
ALTER SYSTEM SET max_replication_slots = 10;
ALTER SYSTEM SET max_wal_senders = 10;

-- 2. replica identity: что попадает в WAL при UPDATE/DELETE
ALTER TABLE events REPLICA IDENTITY FULL;
-- DEFAULT  — только PK (по умолчанию)
-- FULL     — вся старая строка (дорого, но информативно)
-- USING INDEX idx_name — по выбранному UNIQUE-индексу

-- 3. logical slot через pgoutput (нативный плагин):
SELECT pg_create_logical_replication_slot('cdc_app', 'pgoutput');

-- или wal2json — события сразу в JSON:
SELECT pg_create_logical_replication_slot('cdc_json', 'wal2json');

-- 4. для Debezium:
CREATE PUBLICATION debezium_pub FOR TABLE orders, users;
CREATE USER debezium WITH REPLICATION PASSWORD '...';
GRANT SELECT ON orders, users TO debezium;
  • Заброшенный logical slot — главная причина «диск кончился». Если воркер CDC мёртв, primary копит WAL. Мониторь pg_replication_slots.confirmed_flush_lsn.
  • REPLICA IDENTITY DEFAULT + таблица без PK = CDC ловит «событие без before-state». Лечится FULL или USING INDEX.
  • REPLICA IDENTITY FULL пишет всю строку в WAL — дорого на write-heavy. Точечно.
  • Logical replication не передаёт DDL. ALTER TABLE на источнике — руками на приёмнике.
