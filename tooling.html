1. Клиенты

psql, pgcli, DBeaver, PyCharm

CLI-классика и GUI-альтернативы.

# psql — стандартный, есть везде:
psql -h 127.0.0.1 -U postgres -d app

# pgcli — CLI с автодополнением и подсветкой:
pip install pgcli

# DBeaver — кросс-платформенный GUI, поддерживает все мажорные СУБД.
# PyCharm/IntelliJ — встроенные Database Tools, удобны внутри IDE.

Хитрости psql и pgcli

Метакоманды, которые сильно сокращают рутину.

\timing on                       -- показывать время выполнения каждого запроса
\watch 2                         -- повторять последний запрос каждые 2 секунды
\edit                            -- открыть последний запрос в $EDITOR
\copy users TO 'users.csv' CSV HEADER
\copy users FROM 'users.csv' CSV HEADER
\set ECHO_HIDDEN on              -- показывать SQL за метакомандами (\d и т. д.)
\gexec                           -- выполнить результат предыдущего SELECT как SQL
\set HISTSIZE 100000             -- увеличить историю команд
\x auto                          -- авто-режим расширенного вывода
\d   users                       -- описание таблицы
\d+  users                       -- + размеры и комментарии
\df  myfunc*                     -- список функций по маске
\sf  myfunc                      -- показать тело функции
\ef  myfunc                      -- открыть функцию в редакторе

\copy идёт через клиент (используй для локальных файлов), серверная COPY — через сервер. \gexec очень полезен для метапрограммирования: например, «сгенерировать DROP-команды для всех таблиц схемы» — но требует осторожности.

2. .pgpass

Безопасное хранение паролей

Файл ~/.pgpass избавляет от повторного ввода пароля и не светит его в process list.

# ~/.pgpass
# формат: hostname:port:database:username:password
127.0.0.1:5432:*:postgres:secret
prod-db.example.com:5432:app:app_user:abc123def
*:*:replica_db:replicator:repl_secret

# Права обязательны (иначе psql проигнорирует файл):
chmod 600 ~/.pgpass

# Теперь подключение без -W:
psql -h 127.0.0.1 -U postgres -d app

# Альтернатива — переменные:
export PGPASSWORD=secret    # видна в `ps -ef`, лучше избегать
export PGUSER=postgres
export PGDATABASE=app

* — wildcard в любом поле. На Windows файл лежит в %APPDATA%/postgresql/pgpass.conf и про права заботиться не нужно.

3. Размеры БД, таблиц, индексов

Сколько весят данные

Функции pg_database_size, pg_total_relation_size, pg_size_pretty.

-- размер каждой БД:
SELECT datname,
       pg_size_pretty(pg_database_size(datname)) AS size
FROM   pg_database
ORDER  BY pg_database_size(datname) DESC;

-- топ-20 таблиц по полному размеру:
SELECT n.nspname || '.' || c.relname              AS rel,
       pg_size_pretty(pg_total_relation_size(c.oid))  AS total,
       pg_size_pretty(pg_relation_size(c.oid))        AS heap,
       pg_size_pretty(pg_indexes_size(c.oid))         AS indexes
FROM   pg_class c
JOIN   pg_namespace n ON n.oid = c.relnamespace
WHERE  c.relkind = 'r'
  AND  n.nspname NOT IN ('pg_catalog','information_schema')
ORDER  BY pg_total_relation_size(c.oid) DESC
LIMIT  20;

-- размер каждого индекса конкретной таблицы:
SELECT i.indexrelname,
       pg_size_pretty(pg_relation_size(i.indexrelid)) AS size,
       i.idx_scan                                     AS uses
FROM   pg_stat_user_indexes i
WHERE  i.relname = 'orders'
ORDER  BY pg_relation_size(i.indexrelid) DESC;

pg_relation_size — только heap; pg_total_relation_size — heap + TOAST + индексы. Индекс с idx_scan = 0 на боевой системе — кандидат на удаление: место и стоимость записи он жрёт, пользы не приносит.

4. SQLite vs PostgreSQL

Когда SQLite — лучший выбор

Не любая задача требует Postgres. SQLite часто оптимальнее.

SQLitePostgreSQL
АрхитектураВстраиваемая, файл на дискеКлиент-сервер
Конкуренция записиОдин писатель, много читателейМного писателей и читателей
Размер данныхДо нескольких ГБ комфортноГБ–ТБ
ТипизацияType affinity (мягкая)Строгая
РасширенияFTS5, R-tree, JSON1Огромная экосистема
Где братьМобильные приложения, локальные кеши, тесты, CLI-утилитыПродовые бэкенды

SQLite — идеальная встраиваемая БД. Тащить Postgres в моб-приложение или в маленькую CLI-утилиту обычно не нужно. Зато ставить SQLite вместо Postgres в нагруженный веб-сервис — тоже не лучшая идея: один писатель быстро становится бутылочным горлышком.

5. Foreign Data Wrappers

FDW делает чужую БД (Postgres, MySQL, файл CSV, MongoDB) частью локального запроса как обычную таблицу. Главный приз — pushdown ограничений на удалённую сторону.

postgres_fdw и file_fdw

Подключаемся к другой БД через SERVER + USER MAPPING + FOREIGN TABLE. Pushdown — то, ради чего FDW и нужен.

-- подключение к другой Postgres:
CREATE EXTENSION IF NOT EXISTS postgres_fdw;

CREATE SERVER reports_db
  FOREIGN DATA WRAPPER postgres_fdw
  OPTIONS (host 'reports.internal', port '5432', dbname 'analytics');

CREATE USER MAPPING FOR app_user
  SERVER reports_db
  OPTIONS (user 'app_reader', password '...');

-- массовое создание foreign-таблиц:
IMPORT FOREIGN SCHEMA public
  LIMIT TO (orders, line_items)
  FROM SERVER reports_db INTO ext;

-- запрос — как к обычной таблице:
SELECT u.email, count(o.id)
FROM   users u
LEFT JOIN ext.orders o ON o.user_id = u.id
GROUP  BY u.email;

-- CSV через file_fdw:
CREATE EXTENSION IF NOT EXISTS file_fdw;
CREATE SERVER files FOREIGN DATA WRAPPER file_fdw;
CREATE FOREIGN TABLE logs (ts text, level text, msg text)
  SERVER files OPTIONS (filename '/var/log/app.csv', format 'csv', header 'true');
  • Pushdown — главный плюс. Без него JOIN тянет всю удалённую таблицу через сеть. Смотри Remote SQL в EXPLAIN VERBOSE.
  • Транзакционность ОДНОСТОРОННЯЯ: BEGIN на локальной — это не BEGIN на удалённой. Двух-фазный commit FDW не использует.
  • Foreign-таблицы не индексируются локально — фильтры должны pushdown'иться. Если не идёт — переписывай запрос.
  • Не путать с logical replication: FDW — синхронные запросы по требованию; repl — асинхронный поток.

6. Экосистема расширений

Postgres сильнее, чем кажется по коробке. Десяток зрелых расширений закрывает геопоиск, time-series, аудит, планирование заданий, гипотетические индексы и точное измерение bloat.

Топ расширений и pg_cron / hypopg

Не учить наизусть, а знать, что есть и под какую задачу. Установка везде однотипная: CREATE EXTENSION IF NOT EXISTS ….

-- общий механизм:
SELECT * FROM pg_available_extensions ORDER BY name;
CREATE EXTENSION IF NOT EXISTS extname;
SELECT * FROM pg_extension;    -- что включено в этой БД

-- топ-набор:
-- pg_stat_statements  — top тяжёлых запросов
-- pg_trgm             — fuzzy / подстрочный поиск
-- pgcrypto            — gen_random_uuid, hashing
-- citext              — case-insensitive text
-- postgis             — индустриальный геопоиск
-- timescaledb         — hypertables для time-series
-- pg_partman          — ротация партиций
-- pg_cron             — планировщик задач в БД
-- pg_repack           — упаковка без блокировки
-- pgaudit             — аудит DDL/DML
-- pgstattuple         — точное измерение bloat
-- hypopg              — гипотетические индексы

-- пример: pg_cron поверх Postgres
CREATE EXTENSION IF NOT EXISTS pg_cron;

SELECT cron.schedule(
  'cleanup-old-events',
  '0 3 * * *',                                    -- каждый день в 3:00
  $$ DELETE FROM events WHERE ts < now() - interval '90 days' $$
);

-- пример: hypopg — проверить индекс ДО создания
CREATE EXTENSION IF NOT EXISTS hypopg;
SELECT hypopg_create_index('CREATE INDEX ON orders (user_id, created_at DESC)');
EXPLAIN SELECT * FROM orders WHERE user_id = 1 ORDER BY created_at DESC;
SELECT hypopg_reset();
  • Managed-сервисы (RDS, Cloud SQL) часто разрешают только whitelisted расширения. Перед миграцией — сверять со списком провайдера.
  • CREATE EXTENSION требует SUPERUSER. На managed — отдельная роль или web-консоль.
  • hypopg-индексы НЕ существуют физически — это инструмент исследования, видны только в EXPLAIN. Реальные запросы они не ускоряют.
  • Каждое расширение = поверхность атаки. На проде — только то, что действительно нужно.

7. pgbench — нагрузочное тестирование

Идёт в комплекте с Postgres, готов к работе из коробки. Базовый сценарий хорош для сравнения железа и настроек; кастомные скрипты через -f — для проверки своего профиля нагрузки.

pgbench: TPS, latency, кастомные сценарии

Стандартный TPC-B-like сценарий + свой .sql с переменными. Цифры в пресс-релизах надо уметь читать критически.

# инициализация (scale 100 ≈ 1.6 ГБ данных):
pgbench -i -s 100 -h localhost -U postgres bench

# базовый прогон: 50 клиентов, 4 потока, 5 минут, отчёт каждые 10 сек:
pgbench -h localhost -U postgres -c 50 -j 4 -T 300 -P 10 bench

# только чтение:
pgbench -c 50 -j 4 -T 300 -S bench

# кастомный скрипт под свой профиль (my_bench.sql):
#   \set uid random(1, 100000)
#   SELECT * FROM users WHERE id = :uid;
#   SELECT count(*) FROM orders WHERE user_id = :uid;
pgbench -c 100 -j 8 -T 300 -f my_bench.sql -P 10 app

# смешанный read/write 90/10:
pgbench -c 50 -j 4 -T 300 \
  -f read.sql@9 \
  -f write.sql@1 \
  -P 10 app

# через PgBouncer — сравнить с прямым подключением:
pgbench -h pgbouncer.internal -p 6432 -c 200 -j 16 -T 300 bench
  • Сравнивать TPS на разных scale нельзя: -s 1 = всё в кеше; -s 1000 = реальный диск.
  • TPS pgbench ≠ TPS приложения. У реального приложения другие запросы, соединения, latency-распределения.
  • -c 1 -j 1 измеряет сетевой round-trip, а не Postgres. Минимум -c 10 -j 4.
  • Без -P не видно, что TPS просел в середине теста из-за чекпойнта.
  • -T 300 (5 минут) — минимум; короче — пьяные цифры.
