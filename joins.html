Соединения таблиц (JOIN)

Все типы JOIN-ов по отдельности, плюс полу- и анти-соединения через EXISTS, многотабличные запросы и проектирование связей 1:N, N:M, 1:1.

1. Базовые JOIN-ы

Главная операция реляционной БД — соединение таблиц по совпадению значений. Сначала разбираемся с тремя китами (INNER / LEFT / FULL) и одной классической ошибкой: условие на нулевую сторону, ушедшее в WHERE.

INNER JOIN

Только строки, у которых есть совпадение в обеих таблицах.

SELECT u.email, o.id, o.total
FROM   users  u
JOIN   orders o ON o.user_id = u.id
WHERE  u.is_active;

Слово INNER можно опустить — JOIN по умолчанию означает именно его.

LEFT и RIGHT OUTER JOIN

Сохраняет все строки из «опорной» таблицы, даже без совпадения.

-- LEFT: все пользователи, у части — заказы:
SELECT u.email, o.id
FROM   users  u
LEFT JOIN orders o ON o.user_id = u.id;

-- частая ошибка: условие ушло в WHERE — превратилось в INNER:
SELECT u.email, o.id
FROM   users  u
LEFT JOIN orders o ON o.user_id = u.id
WHERE  o.total > 0;          -- LEFT теперь как INNER

-- правильно — внутри ON:
SELECT u.email, o.id
FROM   users  u
LEFT JOIN orders o
       ON o.user_id = u.id AND o.total > 0;

FULL OUTER JOIN

Все строки из обеих таблиц; NULL там, где совпадения нет.

-- сверка двух источников:
SELECT a.id AS a_id, b.id AS b_id, a.amount, b.amount
FROM   ledger_a a
FULL JOIN ledger_b b ON a.tx_id = b.tx_id
WHERE  a.id IS NULL OR b.id IS NULL;

Главный сценарий — найти расхождения между двумя версиями данных.

CROSS JOIN

Декартово произведение: каждая строка с каждой.

-- все комбинации размер × цвет:
SELECT s.id AS size_id, c.id AS color_id
FROM   sizes s
CROSS JOIN colors c;

-- генерим календарь × категории:
SELECT d::date, cat
FROM   generate_series('2026-01-01'::date, '2026-12-31', '1 day') d
CROSS JOIN unnest(ARRAY['food','tech','books']) AS cat;

SELF JOIN

Соединение таблицы с самой собой через два разных алиаса.

-- сотрудник + его руководитель:
SELECT e.id, e.name AS employee, m.name AS manager
FROM   employees e
LEFT JOIN employees m ON m.id = e.manager_id;

Для глубоких иерархий лучше WITH RECURSIVE.

NATURAL JOIN

Автоматически соединяет по столбцам с одинаковыми именами.

-- если в обеих таблицах есть user_id и created_at,
-- NATURAL JOIN неявно использует ОБА столбца:
SELECT * FROM orders NATURAL JOIN payments;

-- Лучше писать явно:
SELECT * FROM orders JOIN payments USING (order_id);
-- или
SELECT * FROM orders o JOIN payments p ON p.order_id = o.id;

NATURAL JOIN ломается, как только в любой из таблиц появится новый столбец с тем же именем (например, created_at). В реальном коде его обычно не используют.

2. Полу- и анти-соединения

Когда нужно «есть ли вообще совпадение» или «совпадений нет» — обычный JOIN неудобен, потому что дублирует строки. EXISTS и его отрицание решают это корректнее.

SEMI JOIN: EXISTS / IN

«У этой строки есть совпадение» — без возврата столбцов второй таблицы и без дублей.

-- EXISTS — обычно лучший выбор:
SELECT u.*
FROM   users u
WHERE  EXISTS (
  SELECT 1 FROM orders o WHERE o.user_id = u.id
);

-- IN с подзапросом — тот же смысл, но осторожнее с NULL:
SELECT * FROM users
WHERE  id IN (SELECT user_id FROM orders);

В отличие от обычного JOIN, semi-join не дублирует пользователя, у которого 10 заказов.

ANTI JOIN: NOT EXISTS / LEFT JOIN ... IS NULL

Строки без совпадения. Два идиоматичных способа.

-- предпочтительно:
SELECT u.*
FROM   users u
WHERE  NOT EXISTS (
  SELECT 1 FROM orders o WHERE o.user_id = u.id
);

-- альтернатива:
SELECT u.*
FROM   users u
LEFT JOIN orders o ON o.user_id = u.id
WHERE  o.id IS NULL;

-- НЕ ИСПОЛЬЗУЙ:
SELECT * FROM users
WHERE  id NOT IN (SELECT user_id FROM orders);  -- ловушка с NULL

Если в подзапросе встретится хотя бы один NULL, NOT IN вернёт пустой результат — и это будет «логически корректно», но почти всегда не то, что ожидал автор.

3. Многотабличные запросы и связи

В реальной схеме редко всё помещается в две таблицы. Здесь — самосоединения, последовательные JOIN-ы, связи через промежуточные таблицы и USING вместо ON.

Соединение более двух таблиц

Цепочки JOIN-ов, читаемое форматирование.

SELECT u.email,
       o.id           AS order_id,
       o.created_at,
       p.name         AS product,
       oi.qty,
       oi.qty * p.price AS line_total
FROM   users        u
JOIN   orders       o  ON o.user_id    = u.id
JOIN   order_items  oi ON oi.order_id  = o.id
JOIN   products     p  ON p.id         = oi.product_id
WHERE  u.is_active
  AND  o.created_at >= now() - interval '30 days'
ORDER  BY o.created_at DESC;

Связь 1:N (один ко многим)

FK в «дочерней» таблице. Не забывай индекс на FK-столбце.

CREATE TABLE users (
  id    bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  email text UNIQUE NOT NULL
);

CREATE TABLE orders (
  id      bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  user_id bigint NOT NULL REFERENCES users(id) ON DELETE CASCADE,
  total   numeric(12,2) NOT NULL CHECK (total >= 0)
);

CREATE INDEX idx_orders_user ON orders (user_id);

Связь N:M (многие ко многим)

Через junction-таблицу с двумя FK и составным PK.

CREATE TABLE posts (id bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY);
CREATE TABLE tags  (
  id   bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  name text UNIQUE NOT NULL
);

CREATE TABLE post_tags (
  post_id bigint NOT NULL REFERENCES posts(id) ON DELETE CASCADE,
  tag_id  bigint NOT NULL REFERENCES tags(id)  ON DELETE CASCADE,
  PRIMARY KEY (post_id, tag_id)
);

-- PK даёт индекс по post_id; для поиска «посты с тегом» нужен второй:
CREATE INDEX idx_post_tags_tag ON post_tags (tag_id);

Связь 1:1 (один к одному)

Общий PK — самый чистый способ.

CREATE TABLE users (
  id    bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  email text UNIQUE NOT NULL
);

CREATE TABLE user_profile (
  user_id  bigint PRIMARY KEY REFERENCES users(id) ON DELETE CASCADE,
  bio      text,
  birthday date
);

Если профиль есть всегда — поля можно держать прямо в users. 1:1 оправдан, когда «вторая» сущность редкая или сильно отличается по жизненному циклу (например, удаляется отдельно).

Упражнения

Использует учебный датасет (скачать). Сначала попробуй сам, потом проверь решение или разбери с ИИ.

1. INNER JOIN: заказы и email покупателя

Покажи o.id, u.email, o.status, o.total для всех заказов. Соедини orders и users по user_id. Отсортируй по o.created_at от свежих к старым.

SELECT o.id, u.email, o.status, o.total
FROM   orders o
JOIN   users  u ON u.id = o.user_id
ORDER  BY o.created_at DESC;

INNER JOIN отбрасывает строки без совпадения. Здесь это безопасно: у каждого заказа всегда есть user_id (NOT NULL + FK).

2. Anti-join: пользователи без заказов

Через LEFT JOIN выведи u.id, u.email пользователей, у которых нет ни одной строки в orders. Не используй NOT IN — он коварен на NULL.

SELECT u.id, u.email
FROM   users u
LEFT JOIN orders o ON o.user_id = u.id
WHERE  o.id IS NULL
ORDER  BY u.id;

Классический паттерн «anti-join через LEFT JOIN + IS NULL». Альтернатива — NOT EXISTS. NOT IN опасен, если правый набор содержит NULL.

3. Топ-3 покупателей по сумме доставленных заказов

Выведи email и сумму его доставленных заказов (status = 'delivered'). Покажи только тех, у кого хотя бы один доставленный заказ. Отсортируй по сумме по убыванию, верхние 3.

SELECT u.email,
       sum(o.total) AS spent
FROM   users  u
JOIN   orders o ON o.user_id = u.id
WHERE  o.status = 'delivered'
GROUP  BY u.id, u.email
ORDER  BY spent DESC
LIMIT  3;

В GROUP BY должны быть все не-агрегированные поля SELECT. Для уникальности достаточно u.id, но u.email тоже разрешён (функционально зависит от PK).

Мини-тест по JOIN-ам

  1. JOIN без префикса — это какой тип соединения?

    По умолчанию JOIN = INNER JOIN.

  2. Условие o.total > 0 попало в WHERE после LEFT JOIN. Что произойдёт?

    Условие из правой таблицы в WHERE отсекает строки с NULL. Чтобы сохранить LEFT — клади условие в ON.

  3. Какой запрос корректно находит пользователей без заказов?

    NOT EXISTS и LEFT JOIN … IS NULL работают всегда; NOT IN ломается, если правый набор содержит NULL. Вариант (c) — это INNER JOIN, и в нём строк с o.id IS NULL по определению нет.

  4. Когда полезен FULL OUTER JOIN?

    FULL OUTER возвращает всё из обеих таблиц + NULL там, где совпадения нет — идеально для diff двух наборов.

  5. Что делает NATURAL JOIN?

    Неявно по всем одноимённым столбцам — отсюда хрупкость.
