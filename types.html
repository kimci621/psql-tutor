PostgreSQL · Типы данных

Типы данных в PostgreSQL

Числа, строки, ENUM, boolean, массивы. JSON/JSONB и работа с датой и временем — на главной странице шпаргалки и в Senior-разделе. Хороший выбор типа закладывает корректность и производительность на годы вперёд.

1. Зачем нужны типы

Зачем нужны типы данных

Тип — это контракт. Он отбраковывает мусор и сообщает планировщику, как хранить и сравнивать значения.

В text можно положить «понедельник» и «13/13/2026». Когда придёт момент посчитать «сколько заказов за прошлый месяц», окажется, что половина строк не парсится. Правильный тип на этапе схемы — самый дешёвый способ предотвратить такие баги.

2. Числа

Числовые типы

smallint / integer / bigint, numeric (точная), real / double precision (с плавающей точкой).

CREATE TABLE money_demo (
  qty       integer        NOT NULL CHECK (qty >= 0),
  price     numeric(12,2)  NOT NULL,   -- точная арифметика
  weight_kg double precision           -- быстрая, но с погрешностью
);

-- классическая ловушка float:
SELECT 0.1::double precision + 0.2::double precision;   -- 0.30000000000000004
SELECT 0.1::numeric          + 0.2::numeric;            -- 0.3

Деньги — всегда numeric(12,2). Целочисленные счётчики — integer или bigint. double precision — для научных вычислений, где погрешность приемлема, и измерений.

3. Строки

Строковые типы

text, varchar(n), char(n), bytea — и почему чаще всего нужен только text.

CREATE TABLE strings_demo (
  body  text,           -- любая длина, без ограничений; рабочая лошадка
  code  varchar(16),    -- ограничение по длине; внутри хранится так же, как text
  fixed char(8),        -- фиксированная длина с дополнением пробелами (почти не нужно)
  raw   bytea           -- произвольные байты
);

SELECT length(body), char_length(body) FROM strings_demo;
SELECT lower(body), upper(body), trim(body) FROM strings_demo;
SELECT body || ' (правка)' FROM strings_demo;

В Postgres varchar(n) не быстрее text: длина проверяется отдельной операцией. char(n) заполняет пробелами до длины — обычно не то, что нужно. Для бинарных данных — bytea, но для крупных файлов лучше внешнее хранилище.

4. ENUM

Перечисления (ENUM)

Строгий список значений, заданный на уровне типа.

CREATE TYPE order_status AS ENUM ('new','paid','shipped','cancelled');

CREATE TABLE orders (
  id     bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  status order_status NOT NULL DEFAULT 'new'
);

-- добавить новое значение можно:
ALTER TYPE order_status ADD VALUE 'returned';
-- порядок определения определяет сравнение
SELECT 'new'::order_status < 'paid'::order_status;   -- TRUE

Удалить значение из ENUM нельзя — только пересоздать тип. Если набор значений динамический, используй обычную таблицу-справочник + FK. ENUM хорош для редко меняющихся, технических наборов.

5. Boolean

boolean

TRUE / FALSE / NULL и удобные литералы.

CREATE TABLE flags (
  user_id   bigint PRIMARY KEY,
  is_active boolean NOT NULL DEFAULT true
);

-- читать стоит без = TRUE — короче и идиоматичнее:
SELECT * FROM flags WHERE     is_active;
SELECT * FROM flags WHERE NOT is_active;

-- Postgres принимает много вариантов литералов:
SELECT 'yes'::boolean, 't'::boolean, 1::boolean, 'no'::boolean;

Помни про трёхзначную логику: WHERE is_active отбирает только TRUE; строки с NULL отбрасываются. Если важно тоже — пиши WHERE coalesce(is_active, false) или IS NOT FALSE.

6. Массивы

Массивы

Массив любой размерности из любого типа. Удобно — но нормализация часто лучше.

CREATE TABLE posts (
  id   bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  tags text[] NOT NULL DEFAULT '{}'
);

INSERT INTO posts (tags) VALUES
  (ARRAY['sql','postgres']),
  ('{python,db}');                       -- литерал тоже работает

SELECT * FROM posts WHERE 'sql' = ANY (tags);
SELECT * FROM posts WHERE tags @> ARRAY['sql','postgres'];   -- содержит все
SELECT id, unnest(tags) AS tag FROM posts;                   -- развернуть

-- индекс для @> и ANY:
CREATE INDEX idx_posts_tags ON posts USING gin (tags);

Массивы хороши для коротких атрибутов вроде тегов. Если в массиве сотни значений, по которым ходят сложные условия — это сигнал нормализовать в отдельную таблицу. Индексы у массива 1-based: tags[1].

7. Дата и время

У Postgres есть полноценные временные типы — пользоваться text или bigint для дат стыдно. Главное правило: для прикладных меток времени почти всегда timestamptz, не timestamp.

date, time, timestamp, timestamptz, interval

Пять основных типов даты и времени, и почему timestamptz — дефолт.

CREATE TABLE events (
  id          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  day         date         NOT NULL,           -- только дата, без времени
  start_at    timestamptz  NOT NULL,           -- момент времени с TZ
  duration    interval     NOT NULL DEFAULT '0',
  local_time  time         NOT NULL DEFAULT '00:00'  -- время без даты
);

-- арифметика:
SELECT now() - interval '7 days';
SELECT start_at + interval '1 hour 30 min' FROM events;
SELECT age(timestamp '2026-05-13', '1990-01-01');

-- усечение и интервалы:
SELECT date_trunc('hour', now());
SELECT extract(epoch FROM (end_at - start_at)) AS seconds FROM sessions;
  • timestamptz хранит UTC + конвертирует в TZ клиента; timestamp — просто наивное «настенное время», его легко сравнить с другой такой же наивной отметкой и получить смещённый результат.
  • date и time — без часового пояса. timetz существует, но его обычно избегают.
  • interval — особый тип; складывается с timestamp и сам с собой. Хорошо работает в SET LOCAL statement_timeout = '2s'.

8. UUID

Когда нужны идентификаторы, которые не угадываются по порядку и могут генерироваться на клиенте. У них своя цена — об этом ниже.

uuid: v4 vs v7, генерация, индексы

128-битный идентификатор, занимает 16 байт. Главный выбор — v4 (случайный) или v7 (со временем в старших битах).

CREATE EXTENSION IF NOT EXISTS pgcrypto;   -- gen_random_uuid()

CREATE TABLE accounts (
  id         uuid       PRIMARY KEY DEFAULT gen_random_uuid(),
  email      text       NOT NULL UNIQUE,
  created_at timestamptz NOT NULL DEFAULT now()
);

-- Подача uuid из приложения:
INSERT INTO accounts (id, email)
VALUES ('01918b6a-7c45-7d31-9a3f-1a4b3c5d6e7f', 'a@example.com');

-- Версия:
SELECT uuid_version('01918b6a-7c45-7d31-9a3f-1a4b3c5d6e7f'::uuid);
  • v4 (случайный) — плохой ключ для b-tree: вставки рандомные, индекс фрагментируется. Хорошо, если порядок не важен.
  • v7 (timestamp + random) — почти как bigint identity по локальности; почти всегда лучше v4 как PK.
  • Сравни с bigint identity: uuid в 2 раза тяжелее, но генерится на клиенте без roundtrip к БД.

9. JSON и JSONB

Когда схема не фиксирована или поля «опциональны и редко». jsonb — почти всегда правильный выбор; json хранит исходный текст без парсинга.

jsonb: операторы и индексы

Доступ через -> / ->>, поиск через @>, индекс GIN.

CREATE TABLE docs (
  id   bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  data jsonb  NOT NULL
);

-- доступ:
SELECT data->'user'->>'email' AS email FROM docs;

-- поиск:
SELECT * FROM docs WHERE data @> '{"role":"admin"}';

-- индекс:
CREATE INDEX docs_data_gin ON docs USING gin (data);

-- если только @>, можно компактнее:
CREATE INDEX docs_data_gin_path ON docs USING gin (data jsonb_path_ops);
  • -> возвращает jsonb, ->> — text. Путать их — типичный источник ошибок сравнения.
  • jsonb — бинарный, парсит при INSERT и убирает дубли ключей; json — текст, дешевле на запись, дороже на чтение.
  • Подробности GIN-индексов и JSONPath — на странице шпаргалки.

10. Двоичные данные

Если нужно положить в БД блоб байтов — не base64-строку, а именно байты, — это bytea. Большие файлы храните за пределами БД (S3) и держите в Postgres только метаданные.

bytea — массив байтов

Бинарные данные переменной длины. Формат вывода — \x hex по умолчанию.

CREATE TABLE files (
  id      bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  sha256  bytea  NOT NULL UNIQUE,
  body    bytea  NOT NULL          -- небольшие блобы; крупные — в S3
);

-- литерал hex:
INSERT INTO files (sha256, body)
VALUES (decode('a1b2c3d4', 'hex'), decode('48656c6c6f', 'hex'));

SELECT id, encode(sha256, 'hex') FROM files;
SELECT octet_length(body) AS bytes FROM files;
  • Постгрес умеет хранить большие значения через TOAST (со сжатием), но всё равно при выборке тянет блоб целиком. Для крупных файлов — внешнее хранилище.
  • Существует ещё «large objects» (lo-API) — почти всегда не нужно, лучше bytea.
  • Когда хочется хранить хэш — bytea(32) для SHA-256 экономит место против hex-строки.

11. Сетевые типы

IP-адреса, подсети и MAC — отдельные типы со встроенной валидацией и арифметикой. Хранить адрес как text — лишний шанс получить «1.2.3.4 » или «1.2.3.04» с пробелом.

inet, cidr, macaddr

IP-адрес с маской, подсеть, MAC-адрес — и операторы для них.

CREATE TABLE access_log (
  id       bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  client   inet   NOT NULL,
  network  cidr   NOT NULL,
  mac      macaddr
);

INSERT INTO access_log (client, network, mac)
VALUES ('192.168.1.42/24', '10.0.0.0/8', '08:00:2b:01:02:03');

-- содержится ли адрес в подсети:
SELECT * FROM access_log WHERE client << cidr '192.168.0.0/16';

-- из IPv4 в IPv6 и обратно (если совместим):
SELECT host(client), masklen(client), family(client) FROM access_log;
  • inet — адрес ± маска (одна машина); cidr — подсеть (хост-биты обязаны быть нулями).
  • Операторы: <<, <<=, >>, >>= — «содержится в», «содержит».
  • Под индекс — GiST с inet_ops для запросов по диапазонам сетей.

12. Диапазоны (range)

Когда «от-до» — это естественная сущность: интервал бронирования, цена в диапазоне, период действия. Постгрес умеет работать с такими интервалами как с единым значением и проверять пересечения индексно.

int4range, tstzrange, daterange, multirange

Диапазон одного из подтипов с включением/исключением границ.

CREATE TABLE bookings (
  id      bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  room_id int NOT NULL,
  during  tstzrange NOT NULL,
  EXCLUDE USING gist (room_id WITH =, during WITH &&)   -- запрет наложений
);

INSERT INTO bookings (room_id, during)
VALUES (1, tstzrange('2026-05-13 10:00+03', '2026-05-13 12:00+03', '[)'));

-- операции:
SELECT lower(during), upper(during) FROM bookings;
SELECT * FROM bookings WHERE during @> timestamptz '2026-05-13 11:00+03';
SELECT * FROM bookings WHERE during && tstzrange(now(), now() + interval '1h');

-- multirange — набор диапазонов как одно значение (PG 14+):
SELECT '{[1,4), [7,10)}'::int4multirange;
  • Скобки [ и ] включают границу, ( и ) — исключают. Каноничный «дискретный» диапазон в Postgres всегда [..) — закрытый слева, открытый справа.
  • Самый сильный сценарий — EXCLUDE USING gist (... WITH &&): БД сама не даст вставить пересекающийся интервал.
  • Под индекс пересечений (&&, @>) — GiST.

13. Геометрические типы

Встроенные point/line/polygon — нишевые. Для серьёзной геометрии все пишут на PostGIS, но базовые геометрические типы полезны для простых сценариев и обучения.

point, line, polygon и PostGIS

Базовая геометрия из коробки и расширение PostGIS для всего серьёзного.

-- встроенные:
SELECT point(1, 2);
SELECT point(0,0) <-> point(3, 4) AS distance;        -- 5
SELECT polygon '((0,0),(0,4),(4,4),(4,0))' @> point(1,1);  -- true

-- PostGIS — индустриальный стандарт:
CREATE EXTENSION IF NOT EXISTS postgis;

CREATE TABLE places (
  id   bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  name text NOT NULL,
  geom geography(Point, 4326) NOT NULL
);

CREATE INDEX places_geom_gix ON places USING gist (geom);

SELECT name
FROM   places
WHERE  ST_DWithin(geom, ST_MakePoint(37.6, 55.7)::geography, 1000);
  • Встроенные геометрические типы оперируют декартовой плоскостью без учёта сферы Земли — для геоданных бери PostGIS.
  • В PostGIS два мира: geometry (плоскость, быстро) и geography (сфера, корректные расстояния).
  • Индекс под пространственные запросы — GiST или SP-GiST.

14. Композитные и доменные типы

Когда хочется свой тип с именованными полями или собственное «суженное» представление существующего. Используется редко, но даёт чистый код там, где сильно нужно.

Композитные типы (row types)

Свой тип с именованными полями. По сути — типизированная строка.

CREATE TYPE address AS (
  city   text,
  street text,
  zip    text
);

CREATE TABLE customers (
  id   bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  name text    NOT NULL,
  addr address NOT NULL
);

INSERT INTO customers (name, addr)
VALUES ('Анна', ROW('Москва','Тверская 1','125009'));

SELECT name, (addr).city FROM customers;

В большинстве случаев отдельные колонки в основной таблице удобнее, чем композит — поля видны через \d, индексируются как обычно, понятны в EXPLAIN.

Доменные типы

Тип с собственным CHECK и значением по умолчанию. «Брендированный» алиас существующего типа.

CREATE DOMAIN email AS text
  CHECK (VALUE ~* '^[^@]+@[^@]+\.[^@]+$');

CREATE TABLE users (
  id    bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
  email email  NOT NULL UNIQUE
);

INSERT INTO users (email) VALUES ('bad');   -- ERROR: violates check
INSERT INTO users (email) VALUES ('a@b.co');

Домен — отличный способ запретить мусор на уровне БД, не таская копию CHECK в каждую таблицу. Минус — менять правило сложнее, чем подправить CHECK на одной колонке.

15. Куда ещё посмотреть

Что осталось за рамками — узкоспециальные типы и темы, у которых есть свои страницы.

Полнотекстовый поиск, деньги, XML и редкие типы

Ссылки на смежные страницы и краткий обзор того, что нечасто пригождается.

  • tsvector / tsquery — типы под полнотекстовый поиск.
  • Какой тип для денег — numeric vs копейки в bigint vs money (последний почти всегда не нужен).
  • XML — официально есть, реально почти не используется. Если выбор между XML и JSONB — это JSONB.
  • Bit strings (bit, bit varying) — фиксированной длины битовая последовательность. Узкая ниша, обычно достаточно integer с битовой арифметикой.
  • Pseudo-types (anyelement, regtype, void) — используются в сигнатурах функций PL/pgSQL, не в обычных таблицах.
  • Приведение типов (::type, CAST) — на шпаргалке.
