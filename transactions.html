Транзакции, ACID и уровни изоляции

ACID-гарантии, savepoints, материализация CTE, и подробный разбор всех уровней изоляции по отдельности — что именно меняется и какие аномалии возможны.

1. ACID

ACID — четыре буквы за словом «транзакция»

Atomicity, Consistency, Isolation, Durability.

  • A — Atomicity. Транзакция либо вся применяется, либо вся откатывается. Между «полу-применённое» состояние недопустимо.
  • C — Consistency. После транзакции БД остаётся в валидном состоянии: все ограничения (FK, CHECK, UNIQUE) выполнены. Это не «согласованность» из CAP-теоремы.
  • I — Isolation. Параллельные транзакции не видят промежуточных результатов друг друга. На практике — спектр уровней (см. ниже).
  • D — Durability. Закоммиченные изменения переживают падение сервера. В Postgres за это отвечает WAL и fsync.

2. CTE и материализация

CTE: MATERIALIZED vs NOT MATERIALIZED

С PG 12+ planner может встраивать CTE в основной запрос. Иногда нужен явный барьер.

-- по умолчанию (PG 12+):
WITH heavy AS (
  SELECT id, expensive_func(x) AS v FROM big
)
SELECT * FROM heavy WHERE v > 0;

-- явно материализуем — CTE выполнится один раз:
WITH heavy AS MATERIALIZED (
  SELECT id, expensive_func(x) AS v FROM big
)
SELECT * FROM heavy WHERE v > 0;

-- явно встраиваем — даже если ссылка единственная:
WITH heavy AS NOT MATERIALIZED (
  SELECT * FROM big
)
SELECT * FROM heavy WHERE id < 100;

Если внутри CTE — медленная функция, и ссылок несколько, MATERIALIZED сэкономит время. В EXPLAIN видно: CTE Scan — материализован; иначе — встроен в основной план.

3. Savepoints

Точки сохранения

Частичный откат внутри одной транзакции.

BEGIN;
  INSERT INTO orders (user_id, total) VALUES ($1, $2) RETURNING id;

  SAVEPOINT before_items;
  INSERT INTO order_items (...) VALUES (...);
  -- если что-то пошло не так:
  ROLLBACK TO SAVEPOINT before_items;

  -- продолжаем работу:
  INSERT INTO order_items (...) VALUES (...);
  RELEASE  SAVEPOINT before_items;   -- savepoint больше не нужен
COMMIT;

ORM-ы используют savepoints для эмуляции «вложенных транзакций». Десятки тысяч savepoint в одной транзакции — это десятки тысяч сабтранзакций; на больших объёмах они начинают тормозить кластер.

4. Уровни изоляции

По отдельности — что меняется на каждом.

READ UNCOMMITTED / READ COMMITTED

В Postgres первый ведёт себя как второй. READ COMMITTED — уровень по умолчанию.

BEGIN ISOLATION LEVEL READ COMMITTED;
  SELECT balance FROM accounts WHERE id = 1;   -- 1000
  -- параллельная транзакция COMMIT-ит UPDATE
  SELECT balance FROM accounts WHERE id = 1;   -- может стать 1500
COMMIT;

Каждый запрос получает свой снимок. Dirty read в Postgres невозможен ни на одном уровне. Non-repeatable read возможен — два одинаковых SELECT внутри одной транзакции могут вернуть разное.

REPEATABLE READ

Снимок берётся один раз в начале транзакции и больше не меняется.

BEGIN ISOLATION LEVEL REPEATABLE READ;
  SELECT balance FROM accounts WHERE id = 1;   -- 1000
  -- параллельная транзакция COMMIT-ит UPDATE
  SELECT balance FROM accounts WHERE id = 1;   -- по-прежнему 1000

  UPDATE accounts SET balance = balance - 100 WHERE id = 1;
  -- возможно: ERROR: could not serialize access due to concurrent update
COMMIT;

Защищает от non-repeatable read и phantom read внутри снимка. Не защищает от write skew: две транзакции читают одно состояние и пишут разное — обе коммитят.

SERIALIZABLE

Эффект параллельных транзакций должен совпадать с каким-то их последовательным выполнением.

BEGIN ISOLATION LEVEL SERIALIZABLE;
  -- запросы и обновления;
COMMIT;
-- При SQLSTATE 40001 (could not serialize access) —
-- сделать backoff и повторить транзакцию целиком.

-- В приложении это выглядит примерно так:
-- for attempt in 1..MAX_ATTEMPTS:
--   try:
--     run_transaction()
--     break
--   except SerializationFailure:
--     sleep(backoff(attempt))

Реализация называется SSI — Serializable Snapshot Isolation. Гарантия корректности достигается ценой retry: при конфликте Postgres откатывает одну из сторон. Удобно для бизнес-логики, тяжело — для горячих счётчиков (там лучше явные блокировки).

Упражнения

Использует учебный датасет (скачать). В транзакционных задачах важна не только формулировка SQL, но и порядок команд — отрабатывай его в textarea.

1. BEGIN / COMMIT / ROLLBACK для атомарного переноса

Напиши транзакцию, которая увеличивает in_stock товара с id=1 на 5 и уменьшает у товара с id=2 на 5. Если у второго товара после операции in_stock < 0, всё надо откатить.

BEGIN;

UPDATE products SET in_stock = in_stock + 5 WHERE id = 1;
UPDATE products SET in_stock = in_stock - 5 WHERE id = 2;

-- Проверка инварианта; CHECK на колонке тоже бы сработал.
DO $$
BEGIN
  IF (SELECT in_stock FROM products WHERE id = 2) < 0 THEN
    RAISE EXCEPTION 'in_stock would go negative';
  END IF;
END $$;

COMMIT;

Транзакция объединяет обе записи в один атом: либо обе применятся, либо ни одна. CHECK (in_stock >= 0) на колонке сделал бы проверку автоматической — RAISE EXCEPTION приведёт к ROLLBACK всей транзакции.

2. SELECT FOR UPDATE против lost update

В транзакции прочитай total заказа id = 3, и если он меньше 1000, увеличь его на 100. Сделай так, чтобы между чтением и записью никакая другая сессия не смогла изменить эту строку.

BEGIN;

SELECT total FROM orders WHERE id = 3 FOR UPDATE;

UPDATE orders
   SET total = total + 100
 WHERE id = 3
   AND total < 1000;

COMMIT;

FOR UPDATE берёт row-level lock на читаемые строки до конца транзакции. Альтернатива — оптимистичная блокировка через колонку version.

3. Какой уровень изоляции выбрать

Сценарий: отчёт «активные пользователи и их сумма заказов» делает 2 запроса в одной транзакции — count активных и sum по доставленным. Между запросами не должны появляться/исчезать строки. Какой минимально достаточный ISOLATION LEVEL? Напиши команду установки и оба запроса.

BEGIN ISOLATION LEVEL REPEATABLE READ;

-- запрос 1: count active users
SELECT count(*) FROM users WHERE is_active AND deleted_at IS NULL;

-- запрос 2: sum delivered
SELECT sum(total) FROM orders WHERE status = 'delivered';

COMMIT;

REPEATABLE READ фиксирует снимок данных на момент начала транзакции — все запросы видят одну и ту же версию. SERIALIZABLE дал бы то же и плюс защиту от write skew, но он дороже и здесь не нужен.

Мини-тест по транзакциям

  1. Какой уровень изоляции — по умолчанию в PostgreSQL?

    READ COMMITTED — дефолт. READ UNCOMMITTED в Postgres ведёт себя как READ COMMITTED.

  2. Какая аномалия НЕВОЗМОЖНА в Postgres ни на одном уровне изоляции?

    Postgres использует MVCC и никогда не показывает чужие незакоммиченные изменения.

  3. Что делает SELECT ... FOR UPDATE?

    FOR UPDATE — exclusive row lock, держится до COMMIT/ROLLBACK. FOR SHARE — share lock, слабее.

  4. В каком случае нужен SAVEPOINT?

    SAVEPOINT — точка частичного отката внутри одной транзакции (ROLLBACK TO SAVEPOINT name;).

  5. В Postgres DDL-команда (например, CREATE TABLE)…

    Postgres — одна из немногих СУБД с транзакционным DDL. Это позволяет миграциям быть атомарными.
