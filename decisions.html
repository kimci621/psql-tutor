Что выбрать — короткие деревья решений

Шпаргалка-«если/то» по самым частым «как правильно». Не догма, а starting point. Под каждым деревом — кнопка ИИ-разбора, если хочешь обсудить нюансы.

1. Какой индекс

Подбор индекса под запрос

  • Запрос ищет точное равенство по одной колонке → B-tree.
  • Несколько условий (равенство + диапазон + сортировка) → composite B-tree, порядок: равенство → диапазон → сортировка.
  • jsonb-фильтры (@>, ?, @@) → GIN. Если только @> — берём jsonb_path_ops.
  • Массивы или full-text → GIN.
  • Поиск по диапазону, данные хорошо упорядочены физически (тайм-серии) → BRIN.
  • Поиск по точке/региону, расстояние → GiST + PostGIS / btree_gist.
  • Только небольшая часть таблицы релевантна (например, активные строки) → частичный индекс WHERE ....
  • Запрос использует lower(email) и т. п. → индекс по выражению.
  • SELECT возвращает несколько столбцов и хочется Index-Only Scan → composite + INCLUDE.

2. Какой уровень изоляции

Подбор ISOLATION LEVEL

  • Дефолт без особых требований → READ COMMITTED. Дешевле всего.
  • Один отчёт делает несколько SELECT, между ними не должно появиться ничего нового → REPEATABLE READ.
  • Risk of write skew (несколько процессов читают-пишут пересекающиеся строки) → SERIALIZABLE. Готовься обрабатывать serialization_failure (40001) и повторять.
  • Lost update на конкретной строке (read → modify → write) → READ COMMITTED + SELECT ... FOR UPDATE.
  • Очередь задач (один воркер берёт задачу) → SELECT ... FOR UPDATE SKIP LOCKED.
  • Очень короткое чтение, без записи → READ COMMITTED или вообще SET TRANSACTION READ ONLY (быстрее, особенно на реплике).

3. Какой тип ID

PK: bigint identity vs UUID v4 vs UUID v7

  • Внутренний сервис, ID не светится наружу → bigint GENERATED ALWAYS AS IDENTITY. Маленький, быстрый, индекс плотный.
  • ID светится в URL/API, угадывание чужих ID — проблема → UUID. Лучше v7 (упорядоченный по времени) — сохраняет преимущества B-tree. v4 рандомный, делает вставки разбросанными по индексу.
  • Распределённая генерация ID без координации (несколько источников) → UUID v7 или ULID.
  • Маленькая таблица справочника → smallint или enum.
  • Естественный ключ есть и стабилен (например, ISO-код страны) → его можно использовать как PK, но обычно проще держать суррогатный ID + UNIQUE.

4. Партиционирование vs шардинг

PARTITION vs sharding

  • Огромная таблица (100M+ строк), но один сервер тянет → PARTITION BY RANGE/LIST. Меньше vacuum-боли, быстрее DROP старых данных.
  • Один сервер не тянет по CPU/IO → шардинг (Citus / руками) или вертикальный апгрейд железа.
  • Аналитика только за последние N дней → партиции по дате + DROP старых партиций вместо DELETE.
  • Multi-tenant с очень неравномерными tenants → шардинг по tenant_id или физически разные кластеры для крупных tenant-ов.
  • Перед шардингом — попробуй: индексы, партиционирование, реплику для чтений, материализованные представления. Шардинг — сложно и больно.

5. Хранение денег

numeric / bigint / money

  • Цены, остатки, расчёты → numeric(p, s). Точность фиксированная, никаких проблем округления.
  • Хранить в копейках/центах bigint-ом — допустимо в OLTP с большим объёмом, но придётся делить на 100 в отчётах. Не путай разработчиков.
  • Тип money → не используй. Зависит от lc_monetary, плохо переносится между БД.
  • Не используй float / double precision для денег. Это approximate-типы.
