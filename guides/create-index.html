Как и когда создавать индекс

Индекс — это вспомогательная структура, ускоряющая поиск, но замедляющая запись и занимающая место. Хорошее правило: сначала найди медленный запрос, посмотри его план через EXPLAIN, и только потом думай про индекс. «Накидать индексы про запас» обычно вредно.

Базовый B-tree

Самый частый индекс: равенство, неравенство, диапазоны, сортировка.

CREATE INDEX idx_orders_user_created
  ON orders (user_id, created_at DESC);

Порядок столбцов важен. Индекс (user_id, created_at) отлично работает для запросов с WHERE user_id = ? и опциональным условием по created_at, но плохо — для запросов только по created_at.

CREATE INDEX CONCURRENTLY

Безопасный способ создавать индекс на работающей системе.

CREATE INDEX CONCURRENTLY idx_orders_status
  ON orders (status);
  • не блокирует INSERT/UPDATE/DELETE;
  • не выполняется внутри транзакции;
  • если упал — оставит индекс в состоянии INVALID; его нужно удалить и попробовать снова: DROP INDEX CONCURRENTLY idx_orders_status;

Индекс по выражению

Когда фильтруешь по результату функции — индексируй сам результат.

CREATE INDEX idx_users_email_lower
  ON users (lower(email));

-- работает с этим запросом:
SELECT * FROM users WHERE lower(email) = lower($1);

Главное — точно те же выражения должны быть в WHERE, иначе планировщик индекс не подцепит.

Частичный индекс

Индексируем только подмножество строк, которое реально читают.

CREATE INDEX idx_orders_pending
  ON orders (created_at)
  WHERE status = 'pending';

-- запрос, для которого он построен:
SELECT * FROM orders
WHERE  status = 'pending'
ORDER  BY created_at
LIMIT  100;

Полезен, когда «горячая» подмножество данных значительно меньше всей таблицы — экономит место и стоимость записи.

Другие типы индексов

-- GIN: jsonb, массивы, полнотекстовый поиск
CREATE INDEX idx_docs_data ON docs USING gin (data);

-- BRIN: огромные таблицы с естественным порядком (например, по времени)
CREATE INDEX idx_events_time_brin ON events USING brin (created_at);

-- HASH: только равенство (после PG 10 — журналируется, можно использовать)
CREATE INDEX idx_sessions_token_hash ON sessions USING hash (token);

Проверка: используется ли индекс

EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM orders
WHERE  user_id = 1
ORDER  BY created_at DESC
LIMIT  20;

SELECT indexrelname, idx_scan, idx_tup_read, idx_tup_fetch
FROM   pg_stat_user_indexes
WHERE  relname = 'orders'
ORDER  BY idx_scan DESC;

Индексы с idx_scan = 0 на проде — кандидаты на удаление: они занимают место и тормозят запись.

Когда индекс не помогает

  • таблица слишком маленькая — Seq Scan дешевле;
  • селективность плохая — индекс возвращает половину строк, дешевле прочитать всё;
  • в запросе используется LIKE '%x%' — обычный B-tree бесполезен; нужен trigram-индекс (pg_trgm);
  • устарела статистика — спасает ANALYZE;
  • выражение в WHERE не совпадает с выражением в индексе.
