Индексы: глубокое погружение

Составные индексы и leftmost prefix, уникальные и частичные, индексы по выражению, покрывающие (INCLUDE), типы индексов, селективность и проблема списка покупок.

1. Составные и уникальные

Составные индексы (несколько колонок)

Один индекс по нескольким столбцам и правило leftmost prefix.

CREATE INDEX idx_orders_user_created
  ON orders (user_id, created_at DESC);

-- использует индекс:
SELECT * FROM orders WHERE user_id = 1;
SELECT * FROM orders WHERE user_id = 1 AND created_at >= now() - interval '7 days';
SELECT * FROM orders WHERE user_id = 1
  ORDER BY created_at DESC LIMIT 20;

-- НЕ использует (нет лидирующего столбца):
SELECT * FROM orders WHERE created_at >= now() - interval '7 days';

Эмпирическое правило: сначала столбцы под равенство, потом — под диапазон/сортировку. DESC в индексе — для совпадения с ORDER BY.

Индекс на уникальность

UNIQUE-ограничение и UNIQUE-индекс — две стороны одного.

-- через ограничение (рекомендуется для именованной целостности):
ALTER TABLE users ADD CONSTRAINT users_email_uq UNIQUE (email);

-- через индекс — то же самое физически, но без имени constraint;
-- зато можно по выражению:
CREATE UNIQUE INDEX idx_users_email_lower ON users (lower(email));

-- частичный UNIQUE — уникальность только для подмножества:
CREATE UNIQUE INDEX idx_users_email_active
  ON users (email) WHERE deleted_at IS NULL;

В UNIQUE по стандарту SQL несколько NULL допустимы. ON CONFLICT (col) работает только если по этим столбцам есть UNIQUE/PK.

2. Селективность

Селективность и почему планировщик выбирает Seq Scan

Селективность — доля строк, которые удовлетворяют предикату.

-- Селективность ~ 1/N, индекс точно лучше:
SELECT * FROM users WHERE id = 42;

-- Селективность 50%, Seq Scan дешевле — индекс не поможет:
SELECT * FROM users WHERE is_active;

-- посмотреть, что планировщик знает про столбец:
SELECT attname, n_distinct, null_frac, most_common_vals, most_common_freqs
FROM   pg_stats
WHERE  schemaname = 'public' AND tablename = 'users';

-- сравнить ожидание и факт:
EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM orders WHERE status = 'pending';

Низкоселективные предикаты лечатся частичным индексом (только для нужного значения) или включением другого, более селективного, столбца в составной.

3. По выражению и покрывающие

Индекс по выражению

Индексируем результат функции, а не сам столбец.

CREATE INDEX idx_users_email_lower ON users (lower(email));

-- использует индекс:
SELECT * FROM users WHERE lower(email) = lower($1);

-- НЕ использует — выражение в WHERE другое:
SELECT * FROM users WHERE email = $1;

-- современная альтернатива — generated column:
ALTER TABLE users
  ADD COLUMN email_norm text GENERATED ALWAYS AS (lower(email)) STORED;
CREATE INDEX idx_users_email_norm ON users (email_norm);

Функция в индексе должна быть IMMUTABLE. Выражение в WHERE должно совпадать с выражением в индексе побайтово.

Покрывающие индексы (INCLUDE)

INCLUDE добавляет столбцы в индекс без участия в ключе — открывает Index-Only Scan.

CREATE INDEX idx_orders_user_created_inc
  ON orders (user_id, created_at DESC)
  INCLUDE (total, status);

-- запрос полностью отвечает индексом, без чтения таблицы:
EXPLAIN
SELECT total, status
FROM   orders
WHERE  user_id = 1
  AND  created_at >= now() - interval '30 days';
-- ожидаемый узел: Index Only Scan

Index-Only Scan возможен только когда страница помечена «всё-видима» в visibility map — за этим следит VACUUM. Слишком много INCLUDE-столбцов раздувает индекс и убивает выгоду.

4. Типы индексов

B-tree, GIN, GiST, SP-GiST, BRIN, Hash

Каждый тип под свой класс операторов и данных.

-- B-tree (по умолчанию): равенство, диапазоны, сортировка
CREATE INDEX idx_orders_user ON orders (user_id);

-- GIN: jsonb, массивы, полнотекстовый поиск
CREATE INDEX idx_docs_data ON docs USING gin (data);
CREATE INDEX idx_docs_data_path ON docs USING gin (data jsonb_path_ops);

-- GiST: геометрия, диапазоны, FTS, k-NN
CREATE INDEX idx_events_tsr ON events USING gist (tsrange);

-- SP-GiST: разреженные пространственные структуры
CREATE INDEX idx_phones_prefix
  ON phones USING spgist (number text_pattern_ops);

-- BRIN: огромные таблицы с естественным порядком (time-series)
CREATE INDEX idx_events_time_brin ON events USING brin (created_at);

-- Hash: только равенство, иногда полезен на UUID/токенах
CREATE INDEX idx_sessions_token ON sessions USING hash (token);

5. Статистика и N+1

Расширенная статистика

CREATE STATISTICS для коррелирующих столбцов.

-- Классический случай: country и city зависимы.
-- Без extended stats планировщик считает их независимыми
-- и сильно недооценивает количество строк.

CREATE STATISTICS idx_geo (dependencies, ndistinct)
  ON country, city
  FROM customers;

ANALYZE customers;

SELECT stxname, stxkind FROM pg_statistic_ext;

Проблема списка покупок (N+1)

Один цикл по 1000 пользователей — 1000 запросов в БД.

# Плохо: цикл превращается в N+1 запросов
for user in users:
    orders[user] = db.query("SELECT * FROM orders WHERE user_id = %s", user.id)

-- Хорошо: один SQL с IN или JOIN:
SELECT user_id, json_agg(o.* ORDER BY created_at DESC) AS orders
FROM   orders o
WHERE  user_id = ANY ($1::bigint[])
GROUP  BY user_id;

Включай SQL-логирование в dev-окружении — N+1 видно сразу. На стороне приложения помогают dataloader-паттерны и батчевое чтение по списку id.

Упражнения

Использует учебный датасет (скачать). Сначала придумай свой ответ, потом сравни с эталоном.

1. Какой индекс ускорит запрос

Запрос: SELECT * FROM orders WHERE user_id = $1 AND created_at >= now() - interval '30 days' ORDER BY created_at DESC;. Какой индекс будет наиболее полезен? Напиши CREATE INDEX ….

CREATE INDEX idx_orders_user_created
  ON orders (user_id, created_at DESC);

Композитный индекс по (user_id, created_at DESC) поддерживает и фильтр, и сортировку. Порядок столбцов: сначала равенство, потом диапазон/сортировка.

2. Частичный индекс на «горячую» часть

Большая часть заказов имеет статус delivered, но рабочий запрос ищет только pending и paid. Напиши частичный индекс, который ускорит этот запрос: SELECT * FROM orders WHERE status IN ('pending','paid') ORDER BY created_at;.

CREATE INDEX idx_orders_active_status
  ON orders (created_at)
  WHERE status IN ('pending', 'paid');

Частичный индекс хранит только нужные строки — он меньше, быстрее обновляется и реально полезен под конкретный запрос. Условие индекса должно быть IMMUTABLE, поэтому now() там нельзя.

3. Функциональный индекс

Приложение делает запрос: SELECT * FROM users WHERE lower(email) = lower($1);. Обычный индекс по email здесь не сработает. Создай функциональный индекс, который ускорит этот запрос.

CREATE INDEX idx_users_email_lower
  ON users (lower(email));

Функциональный (выражение) индекс хранит результат выражения. Запрос обязан использовать ровно то же выражение — lower(email) — иначе индекс не подхватится.

Мини-тест по индексам

  1. В композитном индексе (user_id, created_at) запрос WHERE created_at >= now() - interval '7 days' без условия по user_id…

    В composite-индексе ведущий столбец критичен. Без условия по user_id нужен либо отдельный индекс по created_at, либо seq scan.

  2. Запрос SELECT * FROM users WHERE lower(email) = lower($1); ускорит индекс…

    Функциональный индекс по lower(email): запрос обязан использовать ровно то же выражение.

  3. Что НЕЛЬЗЯ написать в условии частичного индекса?

    В условии частичного индекса разрешены только IMMUTABLE выражения. now() — STABLE, не подходит.

  4. Какой тип индекса лучше всего подходит для jsonb-фильтров и массивов?

    GIN — generalized inverted index — стандарт для составных значений: jsonb, массивы, full-text.

  5. CREATE INDEX CONCURRENTLY — это про…

    CONCURRENTLY не блокирует INSERT/UPDATE/DELETE на время создания. Дороже и медленнее обычного CREATE INDEX, но безопасно для прода.
