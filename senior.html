Senior-уровень: производительность, эксплуатация, безопасность

Темы, которые отделяют «знаю синтаксис» от «отвечаю за БД в проде». Здесь меньше базового SQL и больше про планировщик, миграции без даунтайма, пулинг, репликацию, RLS и работу Postgres из приложения.

1. Производительность и план запросов

Чтение планов и поиск тяжёлых запросов.

Чтение EXPLAIN ANALYZE

Узлы плана: Seq Scan, Index Scan, Bitmap, Nested Loop / Hash / Merge Join.

EXPLAIN (ANALYZE, BUFFERS, VERBOSE)
SELECT u.email, count(o.id)
FROM   users u
LEFT JOIN orders o ON o.user_id = u.id
GROUP  BY u.email;

Сравнивай actual rows и rows estimated. Большая разница — устаревшая статистика или сложный предикат. BUFFERS покажет, сколько страниц прочитано из shared buffers и с диска.

pg_stat_statements — top тяжёлых запросов

Главный инструмент поиска того, что реально жрёт CPU и I/O.

CREATE EXTENSION IF NOT EXISTS pg_stat_statements;

SELECT round(total_exec_time::numeric, 1) AS total_ms,
       calls,
       round(mean_exec_time::numeric, 2)  AS mean_ms,
       round((100 * total_exec_time / sum(total_exec_time) OVER ())::numeric, 1) AS pct,
       query
FROM   pg_stat_statements
ORDER  BY total_exec_time DESC
LIMIT  20;

Ищи запросы по total_exec_time, а не по среднему: частый дешёвый запрос может быть дороже редкого тяжёлого.

Настройки планировщика

work_mem, effective_cache_size, random_page_cost.

SHOW work_mem;
SET LOCAL work_mem = '64MB';

-- На SSD имеет смысл понизить:
ALTER SYSTEM SET random_page_cost = 1.1;

-- Подсказать планировщику размер ОС-кеша:
ALTER SYSTEM SET effective_cache_size = '12GB';
SELECT pg_reload_conf();

work_mem применяется к каждому узлу-сортировке/хэшу в каждом подключении — не выкручивай глобально, поднимай локально для тяжёлых ETL.

2. Конкурентность и согласованность

MVCC, advisory locks, шина событий.

MVCC и снимки

xmin/xmax и видимость строк.

SELECT xmin, xmax, * FROM users WHERE id = 1;

SELECT txid_current(), pg_current_snapshot();

-- найти долгие активные транзакции (тормозят VACUUM):
SELECT pid, age(now(), xact_start) AS age, state, query
FROM   pg_stat_activity
WHERE  state <> 'idle'
ORDER  BY xact_start NULLS LAST
LIMIT  10;

Advisory locks — прикладные блокировки

Один воркер на задачу без отдельной таблицы-замка.

-- транзакционная: снимется на COMMIT/ROLLBACK
SELECT pg_try_advisory_xact_lock(hashtext('cron:nightly'));

-- сессионная: нужно явно отпустить
SELECT pg_advisory_lock(42);
-- ... работа ...
SELECT pg_advisory_unlock(42);

LISTEN / NOTIFY

Лёгкая шина событий внутри Postgres.

-- подписчик:
LISTEN order_created;

-- издатель:
NOTIFY order_created, '{"id": 42}';

Сообщения не сохраняются: пропустил подключение — пропустил событие. Хорошо для cache-invalidation; плохо для гарантированной доставки.

Транзакционный outbox

Атомарность бизнес-операции и публикации события наружу.

BEGIN;
  INSERT INTO orders (user_id, total) VALUES ($1, $2) RETURNING id;
  INSERT INTO outbox (topic, payload)
    VALUES ('order_created', jsonb_build_object('id', currval('orders_id_seq')));
COMMIT;

-- воркер забирает события:
SELECT id, topic, payload
FROM   outbox
WHERE  published_at IS NULL
ORDER  BY id
LIMIT  100
FOR UPDATE SKIP LOCKED;

3. Миграции и масштабирование

Без даунтайма, секционирование, репликация.

Безопасные миграции без даунтайма

Паттерн expand → backfill → contract.

-- 1. expand: добавляем новый столбец, код пишет в оба
ALTER TABLE users ADD COLUMN email_norm text;

-- 2. backfill маленькими батчами
UPDATE users SET email_norm = lower(email)
WHERE  id BETWEEN $1 AND $2 AND email_norm IS NULL;

-- 3. ограничения через NOT VALID, потом VALIDATE (без долгой блокировки)
ALTER TABLE users
  ADD CONSTRAINT users_email_norm_nn CHECK (email_norm IS NOT NULL) NOT VALID;
ALTER TABLE users VALIDATE CONSTRAINT users_email_norm_nn;

-- 4. contract: код переходит на email_norm, старый столбец дропается

Любой ALTER TABLE с ACCESS EXCLUSIVE выстраивает за собой очередь. Совмести с SET lock_timeout = '2s'; — лучше упасть и повторить, чем заморозить прод.

Декларативное партиционирование

Большие таблицы разбиваются на партиции по ключу.

CREATE TABLE events (
  id   bigint GENERATED ALWAYS AS IDENTITY,
  ts   timestamptz NOT NULL,
  data jsonb,
  PRIMARY KEY (id, ts)
) PARTITION BY RANGE (ts);

CREATE TABLE events_2026_05 PARTITION OF events
  FOR VALUES FROM ('2026-05-01') TO ('2026-06-01');

CREATE TABLE events_2026_06 PARTITION OF events
  FOR VALUES FROM ('2026-06-01') TO ('2026-07-01');

Старые партиции удаляются мгновенно (DROP TABLE), без VACUUM. Это часто и есть главный мотив секционирования.

Репликация: streaming и logical

Read-replica, failover, выборочная подписка.

-- логическая репликация:
CREATE PUBLICATION app_pub FOR TABLE orders, users;

CREATE SUBSCRIPTION app_sub
  CONNECTION 'host=primary dbname=app user=repl password=...'
  PUBLICATION app_pub;

-- лаг физической реплики:
SELECT now() - pg_last_xact_replay_timestamp() AS lag;

Логическая репликация не передаёт DDL — миграции применяй вручную на обеих сторонах. Для автоматического failover в проде используют Patroni.

PgBouncer и пулы соединений

Pool modes: session / transaction / statement.

; pgbouncer.ini
[databases]
app = host=127.0.0.1 dbname=app

[pgbouncer]
pool_mode          = transaction
max_client_conn    = 5000
default_pool_size  = 20
server_reset_query = DISCARD ALL

В transaction-режиме одно серверное соединение делится между клиентами по транзакциям. Сессионные штуки (LISTEN, временные таблицы, prepared statements) при этом ломаются — учитывай в драйвере.

Бэкапы: обзор и стратегия

Логические (pg_dump) vs физические (pg_basebackup + WAL). Когда и какой использовать.

# Логический бэкап одной БД:
pg_dump -Fc -f /backup/app.dump app

# Физический бэкап кластера + поток WAL для PITR:
pg_basebackup -D /backup/base -X stream -P -R

# Восстановление логического:
pg_restore -d app /backup/app.dump
  • pg_dump — снимок одной БД на уровне SQL. Переносится между мажорными версиями. Не пишет WAL — нет PITR, восстановление до момента запуска.
  • pg_basebackup — физическая копия каталога данных. В сочетании с WAL-архивом даёт PITR (восстановление на любой момент). Та же мажорная версия и архитектура.
  • pgBackRest / WAL-G — production-grade обёртки: дельта-бэкапы, S3, encryption, параллелизм, валидация.

Правило 3-2-1: 3 копии, на 2 разных носителях, 1 — за пределами площадки.

pg_dump / pg_dumpall: форматы и опции

Plain SQL, custom (-Fc), directory (-Fd), tar (-Ft) — что выбрать.

# Plain SQL (по умолчанию) — текст, можно читать глазами:
pg_dump app > app.sql
psql -d app -f app.sql

# Custom (-Fc) — сжатый бинарь, основной формат для pg_restore:
pg_dump -Fc -f app.dump app
pg_restore -d app app.dump

# Directory (-Fd) — каталог, поддерживает параллельный дамп:
pg_dump -Fd -j 4 -f /backup/app_dir app

# Tar (-Ft) — для очень старых сценариев; используется редко:
pg_dump -Ft -f app.tar app

# Глобальные объекты (роли, табличные пространства):
pg_dumpall --globals-only > globals.sql

# Все БД целиком (только для plain-формата):
pg_dumpall -f cluster.sql

# Полезные опции:
pg_dump -Fc --no-owner --no-privileges -f app.dump app
#   --no-owner       — на восстановлении не будет ALTER OWNER
#   --no-privileges  — без GRANT/REVOKE; роли могут отличаться
  • Custom и directory можно частично восстанавливать (--table, --schema) и распараллеливать через pg_restore -j.
  • Plain не годится для частичного восстановления — это просто простыня SQL.
  • pg_dumpall — единственный, кто экспортирует кластерные объекты (роли, тб-spaces). Дампы конкретных БД делай через pg_dump -Fc.
  • Сжатие (-Z) у custom-формата уже включено по умолчанию. Не сжимай ещё раз.

pg_restore -j: параллельное восстановление

Самый дешёвый способ ускорить восстановление большой БД.

# Восстановить custom-дамп в 8 потоков:
pg_restore -d app -j 8 /backup/app.dump

# Сначала схема, потом данные, потом индексы — для контроля:
pg_restore -d app --section=pre-data  /backup/app.dump
pg_restore -d app --section=data -j 8 /backup/app.dump
pg_restore -d app --section=post-data -j 8 /backup/app.dump

# Только конкретную таблицу:
pg_restore -d app --table=orders /backup/app.dump

# Сохранить SQL в файл, не применять:
pg_restore -f restore.sql /backup/app.dump
  • -j работает только с custom (-Fc) и directory (-Fd) форматами.
  • Перед восстановлением выкручивай для целевой БД: maintenance_work_mem, max_wal_size, временно отключи fsync (только если можешь потерять кластер при сбое — для нового кластера это нормально).
  • Секции pre-data (DDL без индексов и FK), data (COPY), post-data (индексы, FK, триггеры) позволяют тонко управлять процессом.
  • Не забудь после восстановления: ANALYZE (статистика) и VACUUM при необходимости.

pgBackRest и WAL-G

Промышленные инструменты для физических бэкапов и PITR.

# pgBackRest: stanza + первый бэкап.
# /etc/pgbackrest/pgbackrest.conf:
[global]
repo1-path=/var/lib/pgbackrest
repo1-retention-full=2
repo1-retention-diff=4
repo1-cipher-type=aes-256-cbc
repo1-cipher-pass=...

[main]
pg1-path=/var/lib/postgresql/16/main

# В postgresql.conf:
archive_mode = on
archive_command = 'pgbackrest --stanza=main archive-push %p'

# Команды:
pgbackrest --stanza=main stanza-create
pgbackrest --stanza=main backup --type=full
pgbackrest --stanza=main backup --type=diff
pgbackrest --stanza=main info
pgbackrest --stanza=main restore --target='2026-05-09 12:00:00' --type=time

# WAL-G — то же, но к S3/GCS из коробки:
wal-g backup-push  /var/lib/postgresql/16/main
wal-g backup-list
wal-g backup-fetch /var/lib/postgresql/16/main LATEST
  • pgBackRest: full / diff / incremental, параллельные бэкап и restore, шифрование, retention, валидация (--check).
  • WAL-G: акцент на облако (S3, GCS, Azure), дельта по страницам, encryption, простая конфигурация в env.
  • Оба умеют PITR: непрерывно архивируют WAL и могут раскатать кластер на момент времени, LSN или имя метки.
  • pg_basebackup голый — это «hello world» бэкапа. На проде используй pgBackRest или WAL-G.

Retention и тестирование

Сколько хранить и как убедиться, что бэкап работает.

# pgBackRest — встроенные ретеншны:
repo1-retention-full=2     # держим 2 полных бэкапа
repo1-retention-diff=7     # 7 дифференциальных
repo1-retention-archive=2  # WAL за период полных бэкапов

# Вручную (rsync/aws s3):
# - daily: 7 дней
# - weekly: 4 недели
# - monthly: 12 месяцев
# - yearly: 3 года

# Контроль валидности:
pgbackrest --stanza=main check
pgbackrest --stanza=main verify

# Регулярно — DR-учения:
# 1. Развернуть кластер из бэкапа в staging.
# 2. Проверить контрольные суммы / SELECT count(*) на ключевых таблицах.
# 3. Зафиксировать RPO/RTO в инциденте.
  • RPO (Recovery Point Objective) — сколько данных можно потерять. С PITR — секунды (последний WAL).
  • RTO (Recovery Time Objective) — сколько идёт восстановление. Зависит от размера и параллелизма.
  • Бэкап, который ни разу не разворачивали, — это не бэкап. Минимум раз в квартал — учения по восстановлению на чистом окружении.
  • Контрольные суммы страниц (initdb --data-checksums) ловят битый сектор до того, как испортит бэкапы.

Чек-лист восстановления

Что делать, когда «упало». В этом порядке, без импровизации.

  1. Зафиксировать инцидент. Время, симптомы, кто заметил. Не трогать прод до плана.
  2. Решить: что восстанавливаем. Только данные? Целиком кластер? До какого момента (PITR)? Куда (тот же сервер, новый, staging)?
  3. Изолировать продакшн. Перевести приложение в read-only / maintenance, чтобы не писать поверх кривого состояния.
  4. Сделать «снимок места преступления». Если есть возможность — сохранить текущее состояние ($PGDATA, логи) до правок. Поможет потом понять причину.
  5. Развернуть бэкап в staging. Никогда не лей восстановление сразу в прод-каталог — испортишь и его.
  6. PITR-таргет. Если PITR: recovery_target_time = 'YYYY-MM-DD HH:MM:SS' в postgresql.conf; для pgBackRest — --type=time --target=....
  7. Проверка целостности. Контрольные SQL: SELECT count(*) по ключевым таблицам, последние транзакции, чек-сы. Сравнить с ожидаемым.
  8. Переключение трафика. Поменять DNS / connection string. Старый кластер выключить, не удалять.
  9. Postmortem. Что случилось, что не сработало, что добавить в чек-лист и алертинг.

4. Безопасность

RLS, безопасные функции, prepared statements.

Row-Level Security

Политики доступа на уровне строк — основа multi-tenant.

ALTER TABLE documents ENABLE ROW LEVEL SECURITY;

CREATE POLICY tenant_isolation ON documents
  USING      (tenant_id = current_setting('app.tenant_id')::bigint)
  WITH CHECK (tenant_id = current_setting('app.tenant_id')::bigint);

-- Из приложения перед запросами арендатора:
SET app.tenant_id = '42';

Владелец таблицы и суперпользователь обходят RLS. Чтобы они тоже подчинялись политикам — ALTER TABLE … FORCE ROW LEVEL SECURITY.

Безопасные SECURITY DEFINER-функции

Функция выполняется с правами своего владельца.

CREATE OR REPLACE FUNCTION audit_log(msg text)
RETURNS void
LANGUAGE sql
SECURITY DEFINER
SET search_path = pg_catalog, public
AS $$
  INSERT INTO audit (msg, who, ts) VALUES (msg, current_user, now());
$$;

REVOKE ALL ON FUNCTION audit_log(text) FROM PUBLIC;
GRANT EXECUTE ON FUNCTION audit_log(text) TO app_user;

Без SET search_path вызывающий может подменить функцию из своей схемы — это классический вектор повышения привилегий.

Prepared statements и SQL-инъекции

Параметризация — и защита, и кэш плана.

PREPARE p (bigint) AS
  SELECT id, total FROM orders WHERE user_id = $1;

EXECUTE p (42);
DEALLOCATE p;

-- В приложении используй placeholders драйвера ($1, ?), никогда не клей строки SQL.

После 5+ выполнений Postgres может перейти на generic plan. Иногда это хуже custom-плана с конкретными значениями — проверяй на тяжёлых запросах.

5. Поиск по тексту

FTS и нечёткий поиск.

Полнотекстовый поиск

tsvector, tsquery, GIN-индекс.

ALTER TABLE articles ADD COLUMN tsv tsvector
  GENERATED ALWAYS AS (
    to_tsvector('russian', coalesce(title,'') || ' ' || coalesce(body,''))
  ) STORED;

CREATE INDEX idx_articles_tsv ON articles USING gin (tsv);

SELECT id, ts_rank(tsv, q) AS rank
FROM   articles, plainto_tsquery('russian', $1) q
WHERE  tsv @@ q
ORDER  BY rank DESC
LIMIT  20;

pg_trgm — нечёткий и подстрочный поиск

Ускоряет LIKE '%foo%' и даёт similarity().

CREATE EXTENSION IF NOT EXISTS pg_trgm;

CREATE INDEX idx_users_email_trgm
  ON users USING gin (email gin_trgm_ops);

SELECT * FROM users WHERE email ILIKE '%example%';

SELECT *, similarity(name, $1) AS s
FROM   users
ORDER  BY s DESC
LIMIT  10;

6. Postgres из веб-приложения

ORM, наблюдаемость, типичные ловушки.

ORM vs raw SQL

Когда ORM помогает, а когда мешает.

-- N+1 в ORM:
-- users.forEach(u => orm.orders.find({ where: { userId: u.id } }))
--   → 1 + N запросов

-- решение 1: eager-load / include
-- решение 2: один JOIN/CTE на стороне БД

WITH u AS (
  SELECT id, email FROM users WHERE is_active
)
SELECT u.email, json_agg(o.* ORDER BY o.created_at DESC) FILTER (WHERE o.id IS NOT NULL) AS orders
FROM   u
LEFT JOIN orders o ON o.user_id = u.id
GROUP  BY u.email;

Включай в драйвере логирование SQL хотя бы в dev-окружении — иначе ORM незаметно превращает один экран в сотни запросов.

Наблюдаемость: метрики и slow log

pg_stat_database, медленные запросы, ожидания блокировок.

SELECT datname, numbackends, xact_commit, xact_rollback,
       blks_read, blks_hit,
       round(100.0 * blks_hit / NULLIF(blks_hit + blks_read, 0), 2) AS cache_hit_pct,
       deadlocks
FROM   pg_stat_database
WHERE  datname IS NOT NULL
ORDER  BY datname;

ALTER SYSTEM SET log_min_duration_statement = '500ms';
ALTER SYSTEM SET log_lock_waits = on;
SELECT pg_reload_conf();

Хороший минимум алертов: cache hit ratio < 99%, рост deadlocks, лаг репликации, idle in transaction > нескольких минут, медленные запросы из pg_stat_statements.

Это второй слой знаний — поверх базовой шпаргалки. ИИ-ментор по каждой теме разберёт сценарий и поможет проверить понимание сократическим методом.
